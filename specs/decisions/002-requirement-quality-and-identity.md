# DR-002: 需求质量与唯一身份

## 状态

已接受：依据用户在 2026-10-24 提出的需求审查、修订及唯一 ID 要求。
本决策补充 [DR-001](001-acceptance-requirement-baseline.md) 的需求编写和身份约定，保持其需求工作与交付验收分离的边界。
用户后续授权的执行范围见 [DR-003](003-self-acceptance-p0-scope.md)，本决策保留需求审查阶段的工作记录。

## 背景

初始需求基线包含 11 个包、119 条外部行为要求。
条目已有包名前缀 ID，但部分表述混合不同触发和职责，或缺少足以区分正确、错误行为的条件。
用户要求按好需求的标准完成 REVIEW、更新需求并为每条需求提供唯一 ID。
本次标准是项目审查准则，不宣称获得某项外部标准认证。

## 决策

### 质量准则

| 维度 | 审查问题 | 处理方式 |
| --- | --- | --- |
| 价值和必要性 | 该要求服务哪个用户决定或避免什么实际损失，是否有用户指令或现行产品约定支持？ | 删除自造目标；补齐已经约定但漏写的行为。 |
| 单一性 | 是否有不同触发、不同责任或可独立失败的结果混在一条？ | 拆成独立事项；同一操作的必要记录字段可作为一个结果的明细。 |
| 明确性 | 主体、前提、触发、结果及范围能否从正文读出？ | 使用条件与可观察结果替代“合理、可靠”等空泛要求。 |
| 可验证性 | 能否说明什么证据支持满足，以及何种反例违反它？ | 给出判据、拒绝条件或状态区别；语义质量保留有依据的人工判断，不假造分数阈值。 |
| 完整性 | 在已确认范围内，正常、空结果、失败、中断、变化及未知状态是否有必要的处置？ | 补齐与用户目标相关且已有依据的缺失分支，不穷举无关组合。 |
| 一致性 | 角色、状态、身份及版本含义是否一致，跨包是否重复或冲突？ | 明确职责归属及行内引用，保留真实旧结果并单独判断当前适用性。 |
| 可追溯性 | 是否能核对来源、稳定 ID 和修订理由？ | 保留旧 ID；在审查记录逐条记录处理，新增项说明依据。 |
| 实现边界 | 是否误把特定项目、语言或实现偏好当成用户必需？ | 只保留已约定的接口、证据和安全边界；项目命令与工具由项目数据确定。 |

### 用语与职责边界

- 宿主指测试流程中负责绑定、校验、执行和保存记录的协调层；AGENT 指承担指定语义任务的模型会话。
- 独立用例评估和执行复审指与用例实现分开的只读会话，不要求不同模型供应商。
- 设计支持程度描述测试代码能验证什么，实际执行描述发生了什么，正式结论由独立复审依据执行证据判定。
- 设计支持充分不表示已经执行通过，引用校验通过不表示语义判断正确，行覆盖率不表示需求已经充分验证。
- 可验证性允许基于实际内容、引用和反例进行语义审查，不以中文比例、字数或关键词替代标题及评估质量。
- 当前运行前提仍为文档声明的 macOS/Linux 等工具条件；跨项目选取能力不等于任意语言、工具或操作系统均已实测支持。

### 身份规则

- 每条产品需求继续使用原生 `<pack>-<N>` 形式，例如 `case-design-13`，同时作为标题锚点和引用身份。
- 完整 ID 在本项目需求树中唯一；包内编号采用未使用的正整数，不要求跨项目全局唯一。
- 保留全部初始 119 个 ID，修订同一事项时不重编号；拆出的事项分配新 ID 并记录来源。
- 新需求不占用旧事项的 ID，后续退役也不将已公开的 ID 分配给其他事项。
- 需求 ID、场景 ID、永久用例 ID 和验收 AT ID 分别标识不同对象，不相互替代。
- 本次没有重写 SPEX 的 `meta.md` 或初始结构决策，执行框架既有的条目身份规则。

### 审查结果与工作边界

- 审查覆盖全部 119 条初始要求，18 条保留原文，101 条修订，新增 33 条拆分或漏写的已有约定，当前共 152 条。
- 新增内容包括完整需求分析、已有规范回填、跨目标场景一致性、准备验证、标题质量、跳过用例、必要缺口依据、ID 注释与共享索引、修复预算和视图异常交互。
- 新增条目的依据来自本对话用户目标及现行 SKILL 操作合同，不以历史测试通过或当前代码实现证明应当如此。
- 本次只更新需求及审查记录，不生成场景、编写验证条目、启动交付验收、修改产品代码或提交 PUSH。
- 各包验证章节继续明确未开展集成/系统验证；结构检查和需求审查结果均不能代替产品符合性证据。

## 影响

- 后续场景设计按完整需求 ID 引用，不能按段落顺序、标题相似或需求包数量替代义务映射。
- 需求质量争议可定位到具体 ID、条件和判据，修订应保留该事项的身份及变化依据。
- 涉及多个独立事项的拆分会增加条数，条数增加本身不代表新增产品能力或质量提升。
- 全部需求的逐条处理及来源保存在仓库 `reviews/requirements-2026-10-24.md`，供核对修订而非认证实现。
