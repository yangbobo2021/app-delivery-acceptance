# case-assessment: 场景用例组的设计评估

## 意图

帮助用户判断当前场景关联用例是否设计合理、充分且避免冗余，并以可理解的证据说明取舍。

本包规定需求目标，不声明当前实现已经符合或通过验收。

## 外部行为

### case-assessment-1

当对某个场景进行用例评估时，单独只读会话的评估 AGENT 应以该场景的条件、操作及预期审视当前实际关联的完整用例组，不用上层或相邻需求扩大必测目标。

### case-assessment-2

当判断场景的设计支持程度时，评估应逐项列出场景原文义务和用例组的共同贡献，分别标记支持、部分支持、不支持或无法判断，不将源码存在断言表述为已经执行通过。

### case-assessment-3

当识别测试设计问题时，评估应指出具体断言、输入或替身如何削弱当前场景的辨错能力，或如何施加没有合同依据的附加限制，不仅凭测试层级或使用 Mock 判为不足。

### case-assessment-4

当建议保留、补充或合并用例时，评估应比较各项对本场景的增量贡献并引用对照用例，不仅因名称相似、返回值相同或代码路径相同认定冗余。

### case-assessment-5

当输出评估意见时，评估应使用与场景一致的语言及结构化字段，先说明支持程度和决定性原因，再分别列出必要缺口、设计问题、待确认项和可选增强，不在摘要与逐项意见中给出相反判断。

### case-assessment-6

当评估引用测试代码时，宿主应核对文件、行范围、连续原文、哈希及条目关系，引用失配时将该评估记录为不可用，不因引用校验通过就宣称语义判断正确。

- 主声明及支持源码均须为有效 UTF-8 文本且不含 NUL 字节，非文本输入应在调用评估 AGENT 前记为不可用，不以替换字符冒充源码。

### case-assessment-7

当评估完成、失败、超时或被关闭时，流程应保存设计意见或对应不可用状态，不由评估阶段改选测试、触发修补、阻止正式执行或给出产品通过及缺陷结论 [[execution-evidence-5](execution-evidence.md#execution-evidence-5)]。

### case-assessment-8

当将一项问题列为必要设计缺口时，评估应同时提供当前场景原文、实际测试依据及现有断言可能放过的具体错误行为，不能仅以尚未执行、采用替身或没有穷举为由要求补测。

### case-assessment-9

当场景明确规定数量、额度、日期或次数的业务阈值时，评估应核对样本能否区分阈值两侧及等于边界，并说明现有断言可能放过的错误比较关系，不引入未约定的精度或极限要求。

### case-assessment-10

当用例以否定断言、聚合结果或最终值支持场景时，评估应核对操作已生效、目标存在及结果归属的证据，不以“最终内容相同”证明“未执行写入”等动作事实。

## 验证

本轮补充独立评估入口的集成验证，不代表全部设计判断场景或被测产品已通过。
历史测试报告不作为本包当前需求已经通过的证明。

### case-assessment-11

当验证独立用例评估入口时，集成测试应通过真实官方 CLI 的 Evaluator 调用核对当前用例组的逐项评价 [[case-assessment-1](#case-assessment-1)]、阈值必要缺口和真实引用 [[case-assessment-9](#case-assessment-9)]、重复请求的版本适用性，以及评估关闭或失败不产生产品判断和执行门禁 [[case-assessment-7](#case-assessment-7)]。

### case-assessment-12

当将评估引用校验迁移到 Node 时，集成测试应核对当前场景原文和选用用例 [[case-assessment-1](#case-assessment-1)]、源码引用及对照依据，并在调用评估 AGENT 前拒绝非文本支持源码 [[case-assessment-6](#case-assessment-6)]，同时拒绝错误路径、过期文件、未关联目标和自相矛盾的充分性结论，不将结构校验解释为语义评估通过。
