# 项目状态与统计口径

适用于项目概览、统计 JSON、逐场景明细及实时刷新。执行事实、已确认结果、后续动作分开保存；视图只读汇总，不创建执行或改写复审。

## 项目全集与分母

查看目录必须包含完整项目场景清单及已有执行、独立复审和用户决策，必要时向 `serve.py` 传多个目录。按 `(project_id, scene_id)` 去重；版本、重跑次数、批次不是新场景。所有场景指标的分母均为这个项目的全部场景数，包括未执行项。只选基本集合或部分等级执行，不缩小项目概览分母；批次进度可以放在详情中，不能冒充项目总进度。

需求与场景使用不同分母。需求总数来自原始需求及已获准纳入验收的规则；`needs_confirmation` 候选规则单列，不计作已确认需求，也不生成执行场景。缺少完整项目清单时说明项目分母缺失，不能拿当前批次数补作项目总数。

## 执行事实

已经发生过一次场景用例执行，就算已执行；同一场景永远只计一次。收据、实际日志或可信的手动操作记录用于证明执行发生，不能要求执行成功、业务路径完成或复审通过后才计入。失败、异常退出、证据不足、已接受风险和较早版本的执行都计入。实际执行过的证据审计用例也计入；它不能证明原业务链路通过。

仅生成用例、排队、准备环境或写了执行意图，尚未实际运行，不算已执行。缺少执行证据时如实说明，不能把命令文字、计划或实现者自评当成已运行。新尝试尚未执行或没有收据，不取消同一场景已有的执行事实。

## 最近一次已确认结果

从该场景已有的、通过对应证据/结构门禁的独立复审和显式用户决策中，取最近一次已确认结论。按结论确认时间或宿主保存的确定顺序选择，不能按页面刷新时间、准备阶段时间或仅文件被复制后的修改时间选择。

- 新一轮仍在准备、执行或等待复审时，保留上一次已确认结果。活动进度可另外显示，不能自动把原通过改成待审查、未执行或“待复验”。
- 已执行且从未形成有效结论，归入“待确认结论”；有执行结果不等于独立通过。
- 新的有效结论替换旧结果；旧证据保留，不能把多个版本的结果重复累加。
- “待复验”“建议重跑”属于下一步动作，不属于结果分类，也不自动使已确认结果失效。
- 接受风险必须来自明确用户决定，记录对应场景、原因、确认时间和依据。由宿主保存单独的用户处置记录并供视图投影使用，不改写原独立复审 JSON，也不让 Reviewer 代替用户接受风险。保留原技术缺陷证据，结果单列 `accepted_risk`，不计通过，也不与产品 BUG 重复计数。

结果源仍保留真实 revision、attempt、收据和复审引用。项目中保留既有通过，不等于新版本已重测；全量版本交付仍须通过同版本完成门禁。代码覆盖率只使用真实采集对应的数据，不能因保留场景通过而转移旧版本行命中。

## 结果分类与合计

每个已执行场景恰好归入一类：

| 类目 | 对应状态 | 规则 |
| --- | --- | --- |
| 通过 | `passed` | 有有效独立通过结论 |
| 发现 BUG | `product_bug` | 当前最近确认结果为产品缺陷 |
| 接受风险 | `accepted_risk` | 用户已明确接受该缺陷/风险，不计入通过或待处理 BUG |
| 需修复／受阻 | `repair_required`、`blocked`、`inconclusive` | 测试需修复、执行受阻或证据不足；明细保留具体原因 |
| 待确认结论 | 尚无已确认结果 | 已发生执行，仍无有效独立结论或用户处置 |

必须满足：

```text
已执行 = 通过 + 发现 BUG + 接受风险 + 需修复／受阻 + 待确认结论
全部场景 = 已执行 + 未执行
每个场景类目的比例 = 该类场景数 / 全部场景数
```

未执行但准备受阻的项仍显示在活动/明细中，不混入“已执行结果”的受阻计数。每个非零结果类目必须可见；不得只在文字中提及接受风险而漏掉它的统计类目。对账失败时暴露缺项/重复项并修复聚合逻辑，不修改证据、不凭空补通过，也不为凑数执行额外测试。

例如项目有 108 个场景，其中 25 个执行过：23 通过、0 BUG、1 接受风险、1 证据不足、0 待确认结论。应显示已执行 `25/108`、通过 `23/108`、BUG `0/108`、接受风险 `1/108`、需修复／受阻 `1/108`，结果之和为 25。这个例子不授权扩大执行范围，也不构成项目全部验收通过。
