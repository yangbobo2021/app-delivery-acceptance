# 场景生成与审查共同标准

先读取 [验收组织与范围](acceptance-organization.md)。完整原始需求不变；独立核验验收组织的双向映射后再生成场景。所有重要情况、反例和检查点均限定于当前已确认范围。先审范围适用性再审完整性；范围外建议不得作为缺口。新契约为 v4；v3 历史记录保留原始含义，不自动认证。

标准版本：`design-quality-v4`。Analyst 与独立 Reviewer 在黑盒与白盒设计、设计修正和完整验收复用设计时都必须读取本文件。生成与审查共用确认需求、业务范围、风险分级和本标准；独立性来自独立分析与核验，不能来自另一套隐含标准。 分级共用 [scenario-priority.md](scenario-priority.md)：从全部需求和整体目标校准核心闭环、重大风险及真正可用的替代路径；生成与独立审查均不得因失败后可修复或调整有效配置而自动降为 P1，也不按比例分配等级。

## 五项共同质量要求

| 标准项 | 生成者提交 | 审查者核验 |
| --- | --- | --- |
| requirement_alignment：需求一致 | 原始需求关联、业务规则、适用条件、明确范围 | 判据有需求依据；不自行增加角色、接口、性能指标或未确认规则 |
| coverage_completeness：重要情况覆盖 | 正常/异常/边界/状态及重要组合的具体覆盖项、对应场景与方法 | 独立从需求推导重要情况，挑战清单遗漏；检查覆盖项是否实际进入方法 |
| method_discrimination：方法判别力 | 可复现前置、顺序操作、可观察判据、证据要求 | 正确行为与错误行为能被区分；拒绝时核对必要状态不变量，允许时核对实际成功，不能只看退出码 |
| fault_detection：错误发现能力 | 使用适用设计技术建立覆盖，不必预写审查者结论 | 提出合理错误实现，指出现有场景如何暴露；若漏出必须举出具体反例 |
| scope_boundaries：范围与边界 | 本轮纳入范围、明确排除项及限制 | 结论只覆盖已确认范围；重要缺口不能用范围说明掩盖 |

选择适用技术，例如等价类、边界值、决策表、状态转换；说明为什么适用。不是每条需求都要用所有技术，不强制场景数量、拆分粒度、工具或自动化方式。一场景包含多组验证与多个场景分别验证，只要意图、覆盖、判据和证据等效，均应认可。设计只说明怎样验收，执行阶段再选择已有/新增用例或模拟人工操作。设计阶段的“covered”是计划覆盖，不是实测通过。

## 完整场景与验收说明

场景是一份可独立理解、执行及评估的验收单元。每个场景内嵌唯一 `acceptance: {description, preconditions, actions, criteria, evidence_expected}`；不生成独立 methods.json、method_ids 或方法复用关系。多组输入、多项检查保留为场景内的分组操作和判据。共用用例或辅助代码属于执行阶段的绑定，不属于场景设计的多对多方法关联。生成与审查都使用这个相同结构；审查检查内嵌说明及全部检查点。description用最多180字符的简短白话段落说明业务背景、检查行为和目的，让用户不依赖标题、ID或操作简称也能理解场景；具体输入、步骤和判据留在后续分项中。

故障探针仅作为内部审查推理材料；用户视图不展示探针名称、数量、单独入口或原始 probe 记录。审查发现的具体缺口必须体现为检查项、场景验收说明或有依据的 findings。

## 生成记录

`scenarios.json` 根字段增加 `design_standard: "design-quality-v4"` 与 `design_basis`（本轮纳入的每条需求一项）：

```json
{
  "requirement_id": "R1",
  "scope": ["同房间重叠拒绝和相接允许"],
  "exclusions": ["本需求没有定义并发请求处理规则"],
  "techniques": [{"name": "边界值分析", "reason": "区分时间相接与实际重叠，防止端点比较错误"}],
  "coverage_items": [{
    "id": "R1-C1", "condition": "已有10:00–11:00预订，新预订从11:00开始",
    "expected": "允许新预订并保留原预订", "scenario_ids": ["SC-R1"],
    "identification_basis": "需求允许边界相接；检查11:00结束后能否从11:00开始，避免将刚好接上误判为重叠。",
    "check_points": [{"id": "accept", "text": "新预订成功且实际保存"}, {"id": "retain", "text": "原预订仍有效且字段保持"}]
  }],
  "limitations": ["覆盖项针对已确认时间规则，不证明其他预约规则"]
}
```

覆盖项应有具体条件与预期，不能只是“边界测试”；方法要包含对应验证。`scope`、`techniques`、`coverage_items` 非空；`exclusions`、`limitations` 为列表，可以为空。每个黑盒场景必须能追溯至至少一个覆盖项。覆盖项只引用关联同需求的黑盒场景；每个场景自身的 acceptance 说明怎样完成检查。需求快照不改写；设计依据和场景/方法一起参与审查哈希。

## 独立审查记录

Reviewer 单独检查需求、设计依据、场景和方法，只写 `coverage_review.json`，不得修改 Analyst 设计。根字段 `design_standard` 与生成标准相同。保留既有 reason、模式/状态、内部 fault_probes、priority_reviews、output_quality，以及需求与场景两项哈希。本轮纳入的每条需求增加：

- `coverage_results`：每个生成覆盖项一条 `{coverage_id, status: "covered" | "partial" | "gap", reason, scenario_coverage}`。`scenario_coverage` 为实际能够检查此项的场景贡献列表，每项 `{scenario_id, covered_point_ids, reason}`；只列此检查项范围内真实进入方法的检查点。reason定位该场景内嵌 acceptance 的具体操作和判据。没有能够验证的场景时列表为空。总 status 按所有场景覆盖点的并集确定：全部为 covered，一部分为 partial，一个都没有为 gap。重复检查同一点不增加完整度。语义是否属实由独立 Reviewer 核验，脚本只校验结构与并集一致。
- `criteria_checks`：五项共同标准各一条 `{criterion, status: "passed" | "gap" | "needs_clarification", reason}`，写具体检查到的内容。
- `findings`：结构化缺口、澄清或建议，见下文；通过时可以包含不影响充分性的建议，但不能有未解决缺口或澄清。
- `scope`、`limitations`：审查结论的具体范围与边界，均为列表，scope 非空。不要把未执行误写成实测结论。

所有计划覆盖项为 covered、五项检查 passed、无未解决缺口/澄清，且既有反事实/分级/产出质量审查合格，才能判 `sufficient`。根 status 为 passed 仅在本轮纳入的每条需求 sufficient 时成立。Reviewer 不能被生成清单限制；发现未列的重要情况时，在 findings 中给出反例。

## 面向用户的检查项对应表

审查详情首先呈现完整的“需求检查项及覆盖情况｜为什么需要检查｜对应场景”表格，用户根据原始需求就能判断遗漏。不要要求用户阅读五项专业标准或长篇通过理由后才能理解。

- 每个 coverage_item 写 `identification_basis`，用白话指出需求原文或必要推论，以及边界、不同状态、条件组合等具体识别思路；不能只写“边界值分析”。
- 第一列明确标注“检查操作：”和“预期结果：”，分别来自 `condition` 和 `expected`。检查操作用白话说明准备什么状态、谁对什么对象做什么；预期结果写成功/拒绝、记录变化及其他记录应如何保持。两段必须可独立理解，不依赖读者先打开方法。不把 A2、δ 等方法内简称写入主表；直接写对象、时段或最小可选时间间隔。需要每次重新准备数据时写“每次检查前重新准备这些预订”，避免“独立初态”等术语。详细方法可保留已定义的简称及实际标识，不能因简化主表而遗漏原有条件或判据。
- `check_points` 为本检查项中必须完成的具体检查点 `{id, text}`，项内ID唯一。按需要区分请求结果、实际保存、原记录保持、各组输入等；不以机械数量或固定拆分规定粒度。多组情况有独立判据时不能合为一个笼统检查点，避免把只测试其中一组误标为完整覆盖。
- Reviewer 从需求独立检查清单是否完整，核验 identification_basis、每个检查点和方法内真实覆盖范围。新增遗漏在 findings 中明确列出；未纳入现有 coverage_item 的缺口也必须成为主表中的“未覆盖”行，不能只藏在详细审查记录里。已对应某个 coverage_item 的 finding 用可选 `coverage_id` 关联，避免显示成重复新检查项。
- 覆盖状态属于检查项，放在第一列：完整覆盖、部分覆盖、未覆盖。部分/未覆盖须列出具体尚缺检查点。两个场景重叠时，在第一列说明重复范围；重复检查不算新增边界，不自动视为设计缺陷。不能以关联场景数量判断完整度。
- 第三列只列实际有贡献的场景完整标题，可点击查看场景及方法；ID用小字辅助。多个场景逐条列出并去重，无对应场景显示“缺少对应场景”。覆盖徽标、缺口与重复说明不得放到场景标题下。
- 五项标准、逐场景贡献理由、反例、设计技术和原始记录保留在展开区。缺字段或无效记录应明确显示不可核验，不能通过标题、ID、截句或计划关联推测覆盖状态。
- 完整覆盖仅表示审查过的测试设计覆盖该项；未执行产品，不生成实测结果。

## 不通过的举证责任

`findings` 每项 `{kind, requirement_basis, condition, ...}`：

- `coverage_gap`：需求依据必须来自确认需求及其必要行为；另必填 `escaping_fault`、`why_existing_misses`、`expected_detection`、`scenario_ids`（可为空表示没有对应场景）。分别解释具体错误、现有场景如何漏过、补充检查如何识别。不允许仅因写法/粒度偏好拒绝设计。
- `requirement_clarification`：写清原文歧义、影响条件，以及 `question`。没有确认依据的新增业务要求不能归为场景缺口。对应 verdict 为 needs_clarification，现有工作流按需求问题返回，不增加新的状态。
- `suggestion`：写 `recommendation` 及 `reason_nonblocking`；说明现有设计已经满足哪些判据、建议只改善什么。建议不能偷偷变成通过的前提。

verdict 为 gap 时至少一条 coverage_gap；needs_clarification 至少一条 requirement_clarification；sufficient 只能有 suggestion 或空 findings。格式检查不能判定语义真实性；独立 Reviewer 必须实际核验。

审查发现标准本身不足时，明确指出需要修订的标准项及需求/风险依据，由 Analyst 按同一更新版本修正、再独立复审。改变共同通过条件必须提升标准版本，并同步更新结构校验与两角色的输入要求；不能在同一版本下悄悄更换标准。不得临时给 Reviewer 独有的验收条件。修正保留原始发现和版本，不用换措辞掩盖缺口。

## 依据与界限

本标准借鉴 ISTQB CTFL 的需求追踪、测试设计技术、错误推测和明确审查退出条件，以及 ISO/IEC/IEEE 29119-4 的测试设计技术。它是本 Skill 的共同质量约定，不宣称标准合规认证，也不保证穷尽所有错误。

- [ISTQB CTFL v4.0.1：1.4.4、3.2.5、4.2、4.4.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- [ISO/IEC/IEEE 29119-4:2021 官方说明](https://standards.ieee.org/ieee/29119-4/7500/)

## 白盒使用同一标准

白盒生成与审查复用以上设计依据、检查点、并集、五项核验及遗漏反例规则；存储位置见 [white-box-rules.md](white-box-rules.md)。目标可以是已确认需求或单独逆向规则，但不能改写需求快照。已有需求下的白盒补充设计独立绑定，与原黑盒设计一起呈现，不自动继承其充分结论。来源核验和业务确认状态单独记录，不替代设计覆盖审查。候选规则的 sufficient 只针对明确声明的候选检查范围，未定业务预期保留待确认标记及限制；确认后更新判据和边界并重新审查，确认前不能执行或判定产品。
