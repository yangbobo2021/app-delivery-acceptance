# Project-neutral acceptance workflow (v3)

This contract separates model judgments from deterministic execution. No project path, test framework, fixture, service, credential, coverage tool, or source-language convention is built into the workflow. The target project supplies those through a frozen request and per-project adapter commands. The Playbook flows cover whole-list analysis, one-target scenario design and one-scene case design/review; the commit reverse route is a single autonomous Agent task; the portable executor and trace viewer use Python's standard library.

## Stage boundaries

1. **Analysis:** preserve the complete confirmed requirements. The preanalysis Playbook accepts `create` or `edit`, produces an overall business goal, confirmed scope and context-only requirement groups, and structurally checks that every original ID remains included. Editing must bind the previous version and user/agent feedback; agent feedback cannot override a user scope decision. It does not generate scenarios or run tests.
2. **Commit/PR reverse analysis, when white-box is requested:** freeze merge base, head, every changed path and the full declared non-test source inventory. One autonomous Agent reads the diff and necessary source, identifies important direct behavior effects, checks its own wording, evidence, overlaps and likely major omissions, and submits one final result. No separate reverse Reviewer or review-revision loop runs. A deterministic gate validates path disposition, versions, hashes, source references, original IDs and independent contract provenance. The Agent's self-check is best effort, not proof of complete impact discovery. A commit does not rewrite original requirements. Only a completed, hash-bound result may enter downstream work; unresolved effects are visible but not executable.
3. **Scenario design:** for each selected requirement or supported rule, pass the entire original requirements list, goal, scope and groups to the scenario Playbook. It outputs scenarios owned by that one target. Related requirements explain dependencies; they do not become additional owners or generate scenes in this invocation. The independent Reviewer checks target coverage, concrete priority causes, overlap and unrelated scope. White-box mode derives already supported reverse rules and frozen source evidence from the completed reverse result. It never treats code as self-authorizing business policy.
4. **Shared project preparation:** once per frozen project/version, identify relevant existing cases, test setup, fixtures, runnable commands, execution environment and available coverage collectors. Keep this catalog project-specific data, not Skill logic. A later scene selects existing/new/manual cases from it and verifies the actual implementation; a catalog entry alone is not evidence that a check ran. If a new case is necessary, implement it in the project's normal test layout before execution.
5. **One-scene attempt:** use one `delivery-trace-v1` manifest per scene and one fresh attempt directory. `prepare` validates references, paths, commands and version hashes; `project` can expose a prepared state; `execute` runs the actual selected case(s) and optional collector; `project` publishes execution and independent judgment. An attempt cannot execute twice or overwrite its evidence. Review may require scene, case design, case code or evidence repair. A case-design gap is re-planned first. For a selected automated case, the host may apply a bounded exact edit only to its declared test file, record intent and before/after hashes, and rerun in a new attempt. Failed or uncertain edits park for inspection. Product BUG requires a credible test and actual failing product evidence. A passed command alone remains `pending_review`.
6. **Top-level scheduling:** bind each job to frozen input hashes and accepted terminal artifacts. For PR work, derive a complete target inventory from frozen behavior impacts, then schedule each target's scene list and each approved scene attempt. The bundled `playbook/v3/pipeline/orchestrator.mjs` manages crash recovery, locks, atomic receipts, fan-out, uncertain launches and optional `pr_completion` final gating. A retry of an uncertain child requires verifying it is no longer active. Changed requirement/scope/PR head/reverse result invalidates dependent jobs; never borrow an old passing verdict.

The analysis and scenario Playbooks must return at their terminal states. Their model roles do not continue into the next stage; the scheduler/host alone starts the next job. The executor runs only from a frozen manifest. An interrupted scene is resumed from its persisted state or restarted as a new attempt after an explicit decision; never replay a potentially completed external effect silently.

## Portable manifest and evidence

All preparation, execution, conversion, merging and presentation must follow the [mandatory coverage-tool contract](coverage-tool-contract.md). Use language/runtime-specific coverage providers and supported mapping/merge/summary APIs. Custom AST denominators, branch matching, V8 hit inference, transpilation reconstruction or hand-built counter merging are forbidden. Adapters may bind evidence, normalize formats/paths and select tool-reported units for a declared scope; they cannot create missing coverage semantics. Preserve collector/converter/statistics names, versions, actual invocations and configurations, and show those tools beside the metrics. Unsupported line or branch data stays explicitly incomplete/unavailable; user restrictions on reruns, review and scope remain binding.

Use `scripts/v3/portable.py` with `prepare`, `execute`, and `project`. The manifest is JSON with:

- `schema: "delivery-trace-v1"`;
- `project`: stable `id`, readable `label`, absolute `root`, `revision`, optional `revision_mode` (`git`, default, or `declared` with `revision_provenance`), and `sources` (project-relative original-source paths). Git mode verifies HEAD; declared mode relies on the stated external version provenance plus hashes for any listed files. A source-free black-box requirement inventory is allowed, but it cannot claim code coverage.
- `requirements`: complete original items with stable `id`, unmodified `text`, and `source`. `reverse_rules` is a separate collection with stable IDs, supported status, independent basis, contract quote when applicable, and changed-code source paths/revision/hashes. Do not put a code-derived rule into the original requirement snapshot. A requirements-only manifest may contain zero scenarios so the live view shows uncovered items before design.
- `change`, for white-box work: base/head revisions, frozen diff hash, and the path/hash of the completed reverse result. The executor checks the approved artifact, current HEAD, original-source hashes and contract quotation before each stage. Unresolved rules do not execute.
- An independent contract may be a project-relative file or a snapshot from another Git repository. External snapshots carry an absolute path, source repository, immutable commit SHA and source-relative path; every stage rechecks the snapshot hash against the declared Git blob before using its quote. The project-specific path is request data, not Skill policy.
- `scenarios`: zero or one scene per slice. A scene has `id`, exactly one `requirement_id`, `title`, `description`, `priority` P0–P3 and its reviewed reason in the design record. The concise description covers conditions, operation and expected outcome in one or two sentences. Related requirements appear in the design input, not as secondary ownership or an extra data layer.
- `bindings`: actual automated cases or manual operations, each with a unique `id`, `scenario_id`, `kind`, `title`, and origin. Automated cases provide project-relative `test_file`, argv `command`, and concrete `success_markers`. Manual operations provide a `procedure`; the script marks them `not_run` unless `manual-results.json` in the attempt directory contains that binding's `status` (`passed`, `failed` or `blocked`), concrete `actual` observation, and an existing local `evidence_path`. The executor hashes that evidence. Do not turn a plan into an observation.
- `coverage`: `unavailable` 必须给出具体能力缺口，`off` 只用于用户明确关闭，二者都不表示零覆盖。旧版 `required` 的单独执行收集器/解析汇总格式仅供历史证据读取；程序在准备和执行入口拒绝它，避免重复执行业务后再补跑另一套统计。需要持续自动采集的冻结 Git 项目走 v4 的已验证专用 provider 与统一执行入口，见 [专用工具规约](coverage-tool-contract.md)。同一源码版本、兼容统计单位和明确原始证据是合并的前提；结果状态不影响真实计数可用性。手工或无源码场景继续使用 v3，并如实报告覆盖率不可用。

The executor records source and case-code SHA-256, manifest SHA-256, project revision, command, exit code, actual log hash, original coverage report hash, line/branch counters, and attempt ID. The assessment file is written by a separate Reviewer with `execution_sha256`, `reviewer`, `status` (`passed`, `product_bug`, `repair_required`, `blocked`) and a concrete `reason`. The projection gate rejects stale hashes and changed evidence. The reviewer must inspect the actual case implementation and raw observations, assess whether all scene checks ran, verify coverage scope and collection relation, and distinguish a product fault from a faulty test. Structural validation never substitutes for this judgment.

## Viewing and conclusions

Run `python3 <skill>/scripts/v3/serve.py <project-assets-directory> [...]` when the first frozen request is written. Supply the complete project scenario catalog and all existing case/result directories; a selected batch alone cannot supply the project denominator. Supplying only `trace.json` cannot show preparation progress. The loopback view refreshes every five seconds and reads only saved artifacts. “正在处理” appears only for running or waiting work; terminal work leaves this area and remains in the trace table.

Apply the [project statistics contract](project-state-statistics.md): every scene ratio uses all project scenes, including unexecuted items; execution is an enduring fact once a case ran, regardless of version or outcome; results retain the latest confirmed conclusion. Accepted risk is a separate category, and the disjoint result categories must sum to executed scenes. If a scene has never received a confirmed result after execution, show pending confirmation. A new attempt remains unreviewed until its own matching assessment exists, but it does not erase the scene's prior confirmed result. “Needs revalidation” is a future action, not a result state. Keep actual evidence/review versions and sources; retaining a project result does not establish that a new revision was tested.

The trace table groups scenes under each original requirement or admitted reverse rule, including unexecuted scenes. Candidate unconfirmed rules remain separate. Each scene shows case/operation → execution fact → latest confirmed result → actual per-attempt coverage. A scene-design review is not an execution judgment. The cumulative panel uses actual coverage attempts, without inheriting prior-version line hits into a new run, and switches among all declared project source, changed files and executable changed lines. Disabled, unavailable and incomplete coverage never displays a fabricated percentage. Branch coverage remains separate. Long text starts at three lines and expands on demand.

Requirement design coverage, passed case count, independent acceptance and code line/branch execution are different measures. The viewer does not infer sufficient requirements coverage from scene count, merge counters from different attempts, or claim final delivery acceptance from a subset. Full acceptance also requires the independently reviewed scenario list to cover every admitted requirement, all required scene attempts and evidence to pass, and no unresolved exclusions or blockers. Show partial verification honestly.

## Invocation and recovery

The analysis, scenario and case Playbooks need Playbook 16 and the Codex adapter. The reverse route uses the Codex adapter directly for one continuous Agent task. Their requests include `project_root` pointing to a Git checkout used as the role working directory; the business inputs are supplied as JSON and are not read from project source by those roles. Run:

```sh
node <skill>/playbook/v3/preanalysis/run.mjs create|edit request.json NEW-output-dir
node <skill>/playbook/v3/reverse/run.mjs request.json NEW-output-dir
node <skill>/playbook/v3/scenarios/run.mjs label request.json NEW-output-dir
node <skill>/playbook/v3/cases/run.mjs label request.json NEW-output-dir
python3 <skill>/scripts/v3/portable.py prepare manifest.json NEW-attempt-dir
python3 <skill>/scripts/v3/portable.py project manifest.json NEW-attempt-dir
python3 <skill>/scripts/v3/portable.py execute manifest.json NEW-attempt-dir
python3 <skill>/scripts/v3/portable.py project manifest.json NEW-attempt-dir
```

Keep the selected test-asset directory fixed for a run. Freeze the original requirements, analysis version, scene review, case implementation and user scope decision hashes before downstream work. Resume only with matching bindings. A new user scope decision creates a new downstream version; old records remain historical evidence. The command runner stores no credentials in manifests or logs; pass secrets through an approved external mechanism and redact evidence as needed.
