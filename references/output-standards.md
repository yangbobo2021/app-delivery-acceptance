# 测试产出物标准

For new designs, also read [acceptance-organization.md](acceptance-organization.md). Explain each unit boundary, original check source, criterion-level admission and global risk in business language. Scope review precedes coverage review; outside-scope suggestions remain nonblocking and visible separately. Keep excluded/context checks and partial conclusion boundaries visible.

本标准适用于本 Skill 新生成和新写入的全部产出物。可读、准确、可复核是交付要求，不是可选的展示优化。生成者按对应标准撰写，独立 Reviewer 检查语义和证据，脚本检查结构、引用和明显占位内容。脚本通过不等于语义审查通过。格式缺失或内容难以理解属于产出质量问题，必须在原设计修正或当前场景的修正环节解决；不得登记为产品 BUG 或凭此判断 AI 无法执行。

## 通用要求

- 第一层说明业务事实或测试结论，下一层按条件、步骤、判据和依据分项。读者不打开原始日志也应理解测试意图、实际行为、结论及边界。
- 使用具体主体、触发条件、操作和可观察结果；一项一个含义。避免“功能正常”“符合预期”“已保存结果”等仅重复状态的句子。不以检查数量、退出码或文件存在替代业务结论。
- 摘要一句话，最多180字符；操作方案说明“怎样验证什么”，执行结果说明“实际发生什么”，独立评估说明“哪些事实符合/不符合哪些判据”。不同摘要不能互相复制来冒充不同角色的判断。
- ID、路径、哈希、选择器和版本用于定位，放在单独字段。技术命令、运行参数、详细追踪保留在技术详情或原始证据中，不占据业务摘要。
- 需求检查项用“检查操作”“预期结果”明确区分要做什么和怎样才算符合要求；用用户、业务对象和具体输入说明，不依赖方法内的数据简称或未解释术语。简化文字必须保留原有检查条件、状态变化和记录保持要求，主表不能冒充实测结果。
- 不用截取长文、自动拆句或模型猜测替代作者的结构化记录。不把计划写成实测，不把执行者的断言写成独立观察。证据缺失明确指出缺什么以及影响哪个判断。
- 优先使用用户指定语言，否则业务文本继承关联原始需求的主要语言；字段名、稳定ID、技术标识和应用原文保持不变。需求快照保持确认原文；模糊输入提问或列入未确认事项，不能擅自改写为新的业务要求。

## 各类产出标准

完整场景、内嵌验收说明及设计审查共用 [场景设计质量标准](design-quality.md)。生成提交范围、所选技术及具体覆盖项；审查按同一五项要求逐项解释，并独立挑战遗漏。不通过必须有需求依据和具体漏出反例；需求澄清与非阻断建议分开，不因等效组织方式不同而拒绝设计。

| 产出物 | 必须表达的内容 | 专业质量检查 |
| --- | --- | --- |
| 需求快照、待确认事项 | 原文、稳定ID、来源、确认版本；待确认项列出问题、影响范围、需要的决定 | 不改业务基线；说明歧义影响什么场景，不能仅写“需求不明确” |
| 项目与资源记录 | 项目启动/测试入口、实际环境、测试代码规范；每个资源的用途、选择理由、验证行为和证据；真实/Mock边界 | 资源名和用途可理解；失败说明原因及影响；不泄露凭据，不把Mock结果当真实集成证明 |
| 测试场景 | 标题说明触发条件和关键行为；关联需求、重要度、具体失败后果；expected写可观察的结果及应保持的不变量；白盒补充分支/状态及业务影响 | 一个明确验收意图；边界、负例、状态转换可辨认；仅看标题与场景说明即可理解检查目的和范围。标题不超过120字符 |
| 场景内嵌验收说明 | description用最多180字符的简短白话段落说明业务背景、检查的行为和目的；具体细节留在后续分项；preconditions列状态与输入，actions列顺序操作，criteria列独立判据，evidence_expected列各判据所需证据 | 场景说明不依赖标题、ID或未解释简称；四项均为非空分项列表；判据有具体内容而非“符合预期”；证据能证明判据；设计阶段不选择已有/新增用例或人工模拟 |
| 设计及重要度审查 | 逐需求的方式/状态/可能漏出的故障、对应场景及可见失败信号；重要度判断及后果；逐类可读性审查 | 不照抄设计自称充分；明确为什么能捕获错误，漏测如何补充；检查场景、方法是否按标准表达 |
| 执行计划、阶段与未测记录 | 冻结场景范围、P0至P3顺序、当前阶段/尝试；未测原因及未验证风险 | 计划不冒充执行；待执行、修正中、已评估、明确未测分开；不补造进度 |
| 单场景执行方案与准备记录 | summary说明如何验证什么；每个用例procedure分开目的、前置/数据、步骤/预期及负责的检查范围，case_design明确联合覆盖；选择理由、已有用例检查、实现位置、输入来源、技术入口独立记录 | 可按步骤复现；方式选择来自需求/代码/场景/方法/已有用例；代码遵循项目规范，用例关联可定位；原始技术细节不混入摘要 |
| 用例代码、夹具与模拟人工操作（逐用例/任务） | 体现所验风险的断言/操作、可复现的输入及清理方式；用例业务名称、本轮已有/新建来源、代码位置、精确用例标识和运行版本；模拟人工记录真实操作及结果 | 不仅检查页面能打开或进程退出0；可追溯场景；修正测试缺陷不修改产品；不虚构点击或人类观察；每个用例/人工任务独立按scenario-execution.md的procedure描述目的、前置数据、操作与预期、对应检查项子范围；与实际代码/操作一致，技术定位折叠，不能照抄场景或把预期写成实测 |
| 执行结果 | summary写关键实际行为；step_results逐项写实际操作/观察/证据；完整actual保留；例外写实际阻碍 | 每个结果来自本次实际行为；说明关键状态前后变化；失败与不充分证据分开；不以断言数量充当结果 |
| 证据清单与原始证据 | 每份文件记录业务名称、实际采集时间、关联步骤/判据、精确路径；原始日志/截图/API/状态数据及哈希保持原样 | 能回答“这份证据证明什么”；截图可辨认关键状态，日志包含输入/实际输出；来源、尝试、版本明确；不能只有启动截图或命令 |
| 独立评估与执行修正 | summary说明关键事实与判据的关系；assessment写范围、逐判据预期/实际/证据、依据、边界及output_quality；修正说明具体质量问题和需补充的行为 | 实际打开证据，不能只引用执行者结论；同时检查操作方案、执行结果、证据的可读性与准确性；普通质量问题repair_required回到同场景 |
| BUG与AI执行异常 | BUG含业务标题、复现条件/步骤、预期/实际、影响、证据、场景/版本；AI异常含能力问题、实际恢复尝试及独立依据 | 问题能被他人复现和定位；BUG仅为确认产品行为错误，能力异常不替代普通修正；发现BUG后继续后续场景，不修产品 |
| 最终验收记录与覆盖关系 | 先给总体结论、验证范围/边界及主要发现；按重要度统计；场景标题、执行摘要、独立判定摘要；BUG/异常/未测风险、证据入口及后续建议；技术门禁诊断分开 | 执行通过不冒充独立通过，部分测试不冒充全部通过；报告与本轮记录一致，摘要有业务含义；海量路径不塞入表格 |
| 可选代码覆盖率产物 | 测量范围、原始来源/工具、计数及分母；未覆盖分支的行为风险、独立处置理由及补充场景；推荐动作与具体漏出故障关联 | 不能用百分比替代行为验收；不可测不写100%；不拼接不同版本数据；标准模式不强制生成 |
| 工作流/审查历史与原始JSON | 明确时间、阶段、尝试、修正原因、当前与历史结论；技术原文保留并折叠 | 元数据辅助追踪而不伪装成业务报告；不重复铺开长文，不隐藏未通过的尝试 |

独立评估必须同时完成测试执行可信性核查和最终验收论证，格式及点击标签的显示要求见 [独立评估标准](independent-assessment.md)。测试本身未核实不得判产品通过或BUG；最终说明必须包含需求、实际操作、预期/实际、决定性证据、推理和边界。

## 强制检查与独立语义审查

1. prepared必须含有实质summary、逐用例procedure和完整case_design；observe必须含有逐用例case_results、实质summary、step_results和覆盖每份引用的evidence_details；evaluate必须含有实质summary和assessment。字段缺失不能推进。保留原始字段和证据绑定。
2. assessment.output_quality格式如下。checks必须覆盖operation_plan、execution、evidence，每项reason指出实际检查到的内容及质量判断。status为passed时findings必须为空；内容有问题使用repair_required并给出具体findings，独立评估也必须为repair_required。产品失败可以有通过的产出质量审查。
3. 黑盒coverage_review.json.output_quality检查scenarios和acceptance，两个类别的record_ids均完整列举本次审查的黑盒场景ID。完整设计检查中white_box_priority_review.output_quality按相同格式覆盖白盒场景及其内嵌验收说明。已有哈希绑定必须更新自真实独立审查。
4. 最终review.json必须有实质summary、scope（included/excluded/limitations分项列表）、recommendations分项列表和output_quality。其checks覆盖project、resources、execution、evidence、issues；coverage模式还覆盖code_coverage。每项写清检查范围和判断，不能只写“可读”或“通过”。project涵盖项目配置、原始需求来源/限制及待确认事项；resources涵盖资源决策和依赖实测；execution涵盖计划、准备记录、用例/夹具及步骤结果；evidence涵盖清单及原始文件；issues涵盖BUG、AI异常、修正与未测说明。可选产物存在时也纳入对应类别检查，明确具体文件和范围。覆盖关系视图直接展示已保存结果，不生成额外文字报告，人工核对摘要、范围、场景结果、风险和建议是否与本轮记录一致，不能补造已执行事实。

```json
{
  "version": 1,
  "status": "passed",
  "checks": [
    {"artifact": "operation_plan", "reason": "方案明确已有预订状态、重复提交步骤和拒绝/记录不变两项判据，技术命令单独保存。"},
    {"artifact": "execution", "reason": "结果逐项记录冲突提示和保存前后记录变化，摘要与实际记录一致。"},
    {"artifact": "evidence", "reason": "截图与状态数据分别关联拒绝提示和记录不变判据，时间及本次路径可核对。"}
  ],
  "findings": []
}
```

示例只说明格式，不证明真实产品行为。设计审查的check另加record_ids；修正评估可以指出未执行方案的实际阻碍，不要求伪造未发生的动作。独立语义检查应问：“另一位测试工程师能否理解意图、复现步骤、核对结果、解释判断和识别限制？”答案为否就修正。不能仅靠词数、字段存在或程序校验宣布专业质量达标。

设计审查的主产物是按需求列出的检查项对应表，遵循 [共同设计标准](design-quality.md#面向用户的检查项对应表)。第一列包含检查项、合计覆盖状态、具体缺口及重复范围；第二列解释识别依据；第三列为完整场景标题及关联。专业核验过程放到展开记录。

白盒场景与补充逆向规则按 [white-box-rules.md](white-box-rules.md) 区分来源、独立判据与待确认状态；逆向规则是单独产物，不改写已确认需求。其正文、检查项、来源和审查原因也必须自包含、易于理解。

项目与资源总配置描述长期适用的项目范围、入口和资源依据，不能把上一轮的“本轮”措辞继续用作新一轮实测声明。每轮实际范围、资源复核和未执行事项以该轮冻结计划、dependency_checks、观察及独立评估为准；保留的输入来源限制必须明确披露，不能借用旧轮实测结论。

场景与用例的信息分工、逐检查点联合覆盖、独立审查case_coverage、逐用例case_results及四列报告遵循 [case-design.md](case-design.md)。场景级operation_plan不是新记录的必需内容；用例过程与证据在具体用例中维护，整体最终结论仍归场景。
