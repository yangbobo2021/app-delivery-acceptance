# 项目验收目录、稳定身份与知识发现规约

本规约适用于所有新的 v3/v4 验收及其恢复。项目根目录是用户项目目录，不是某个产物目录，也不要求等于每个隔离工作树的位置。程序入口为 `scripts/acceptance_store.py`；只组织、校验和读取已有数据，不执行项目用例或知识脚本，不提交 Git、不上传资料、不自动迁移历史。

本次需求、逆向规则和场景的完整冻结定义、可选外部引用及变更流程见[冻结定义契约](frozen-definitions.md)。v2 延用 scenarios.json 与 records/catalog-* 历史，不新建项目 SPEC 管理系统；完整定义属于长期保留资料。

## 三类产物与目录

```text
项目/
├─ <现有测试目录>/                  正式用例、夹具和测试助手，沿用项目规范
├─ .acceptance/                     纳入项目 Git
│  ├─ knowledge/                    跨验收复用的知识、工具、流程
│  │  ├─ INDEX.md                   必读总入口
│  │  ├─ scripts/INDEX.md           按需建立；脚本与使用说明
│  │  ├─ workflows/INDEX.md         按需建立；流程与适用条件
│  │  └─ conventions/INDEX.md       按需建立；项目测试约定
│  └─ AT-<验收测试ID>/
│     ├─ manifest.json             身份、名称、负责人；不绑定一个固定 PR/head
│     ├─ scope.json                当前范围快照的路径、版本和哈希
│     ├─ scenarios.json            项目完整场景清单快照，包括未执行场景
│     ├─ tests.json                正式用例路径、命令、场景 ID 映射
│     ├─ completion.json           可选：已结束验收的精简结论、实际版本及数据清理说明
│     ├─ evidence-index.json       可选：可共享证据身份、哈希和存储位置；无密钥
│     └─ records/
│        ├─ scope-0001.json        不可覆盖的范围与真实决定依据
│        ├─ scope-0002.json        同一验收 ID 下的下一范围版本
│        ├─ catalog-<唯一后缀>.json 不可覆盖的完整场景清单版本
│        └─ evidence-<唯一后缀>/   明确选取、脱敏后可提交的执行/复审/证据包
│           ├─ record.json        文件哈希、范围哈希、来源路径映射
│           └─ <原始相对结构>/    冻结输入、trace、收据、复审及必要证据
└─ .acceptance-local/               不提交 Git，必须加入项目 .gitignore
   ├─ current.json                 当前进行中的验收 ID，不绑定对话
   ├─ current.lock                 启动/结束写入的互斥锁，不代表验收状态
   └─ AT-<同一验收测试ID>/
      ├─ workspace/                 本验收唯一专用工作树：产品代码与项目测试目录
      ├─ workspace.lock             准备、执行、复审串行互斥锁
      ├─ workspace-owner.json       未收尾场景的恢复归属，不因进程退出自动释放
      ├─ knowledge-reads/           实际读取内容的哈希凭证
      ├─ imports/                   历史原件快照、路径映射及本机迁移清单，不作为新执行扫描
      └─ workflows/
         └─ <阶段或尝试名称>/      Agent 输出、runtime/ 安装环境、探针、场景原始证据；不再建立工作树
```

三类仍为：本验收不提交、本验收要提交、跨验收复用且要提交。正式用例属于第三类，但留在现有项目测试体系中；`knowledge` 可以存通用可复用脚本、文档和流程。项目现有助手和夹具优先引用，避免两份实现。不要求预建无内容的知识子目录。

`.acceptance-local` 是验收执行中的本机工作区。验收期间保留判断所需真实证据；验收结束且代码与精简结论已保存后，日志、截图、覆盖率原始数据、依赖和工作树可以清理，不要求长期保留或上传大运行数据。清理条件见[验收结束与本机清理](#验收结束与本机清理)。上传只为共享追踪、结论与复用，不改变场景结果，也不自动授予上传或发送权限。密钥、登录态、环境密文、数据库全量及未经筛选的会话不能进入提交包。

## 一个验收共用一个工作树

默认且当前自动执行入口只支持一个专用工作树：`.acceptance-local/<ID>/workspace`。它是一份完整项目检出，产品代码和正式用例都在项目既有目录中，不是用例目录。准备、用例实现、本地调试、冻结执行及独立复审按场景串行复用；各场景另有 workflows 运行目录，隔离数据库、端口、账户、浏览器上下文和输出，不能把“共用工作树”理解成复用脏业务状态。覆盖率工具必要的临时插桩构建属于运行产物，不是另一个验收工作树。

`prepare_project.py` 从 spec 的 `source_checkout`（缺省 `project_root`）与固定 `revision` 建立/复用 workspace，catalog.project_root 返回 workspace。后续场景 request.project_root、case template.source_checkout 使用此实际目录；acceptance.project_root 始终是用户项目根目录。所有场景复用同一 catalog 与工作树；程序不再创建 `<场景>/checkout`。旧配置和旧工作树保留为历史，只读展示；采用新入口须新建冻结配置，不能改写旧收据来假装过去已经共用工作树。

准备和整段场景执行/复审持有验收级 workspace.lock；不同场景不能并行写入。中断场景保留 workspace-owner.json，必须先恢复/核对该场景，不能通过删除锁/归属文件或开启新场景绕过。每个阶段重查固定提交、组件版本、产品文件哈希和允许的测试修改范围。已完成场景的用例修改可以留在工作树，下一场景复用；冻结收据记录本次实际文件哈希和命令，用例依赖绑定不等于实际执行了这些文件中的全部测试。复审完成后再开始下一场景，不用当前可变用例去冒充过去执行的字节。

产品修复与用例验收是两个阶段。用例 Agent 仍只能改声明的测试目录；产品 BUG 需已有用户修改授权，保存失败结论后在同一 workspace 修复并提交/固定新版本，再准备新 catalog 和受影响的下游尝试。提交/范围变化不换验收 ID，也不自动复用旧版本覆盖率或称新版本通过。程序遇到版本不符只停止，不 reset、切换提交、覆盖现有修改或另建工作树。正式用例直接写进 workspace 的项目测试目录，确认后随代码交付，不先放进 `.acceptance` 再搬一次。

## 验收结束与本机清理

验收结束后长期保留的是小型记录：原始需求及范围版本、场景与判据、场景到正式用例/命令的关系、每场景已执行事实和最近确认结论及理由、实际主仓/组件版本、风险接受/证据不足等用户决定，以及覆盖率工具名称版本、范围和工具生成的统计摘要。汇总可保存为 `.acceptance/<ID>/completion.json`，必要的确认记录仍放 records；tests.json 指向项目正式测试文件。结论引用的真实执行时间与版本不变。工作树可能经历多个修复版本，验收 ID 标识整项工作，不是某个唯一提交。

**验收结束前的检查：**由宿主在现有结束流程中完成，不新增阶段、状态或报告格式：

- 对照确认的范围、完整场景清单和原始执行/复审记录，确认精简记录保留实际版本、最近确认结论、接受风险、证据缺口及未执行范围；各结果分类合计等于已执行数。范围内未完成项必须明确披露，不能借结束操作改成通过，也不要求未选中的全部项目场景通过才能结束。
- 仅当本次包含代码/用例交付、提交、合并或 CI 核对时，依据实际文件、提交及对应检查记录核对交付状态；不能用本地通过代替已提交，或用 PR 检查代替合并后检查。未要求或不适用的事项说明边界，不为结束验收新增 CI、自动合并或扩大授权。
- 阅读保存的精简记录并核对视图的概览、场景结论和引用；长期结论应能脱离将清理的 local 原件读取。已有结构与归档哈希校验复用 `acceptance_store.py check <项目目录> <ID>`；它不证明业务结论正确、代码已交付或相关进程已退出，剩余事项由宿主依据实际记录核对。缺必要资料时先保存限制或补齐资料，不靠重跑测试凑齐结束条件。
- 确认本验收相关执行已结束、结束结论已保存，再按[当前验收指针规约](#当前验收指针与启动恢复结束)调用现有 `finish`；随后用 `current` 确认指针已清除。此操作不认证验收通过。

检查依据写入现有 completion 或结束记录即可；不适用、未验证和已确认的事项分别说明，不能只写“全部检查完成”。

完成上述结束检查且用户授权清理后，再确认修复、正式用例、配置和夹具有可恢复的保存版本，没有仅留在工作树中的独有修改/提交；仅有 detached HEAD 上的独有提交、未提交文件或一份补丁不等于已交付。保留实际命令、工具/组件版本和环境说明，复现不依赖即将删除的绝对路径。通过 Git 正常移除主工作树和组件检出，再清理本验收 local 运行资料；不删除 Git 公共对象库或其他验收资料。

不要求保留日志、截图、原始覆盖率供将来复核；可按用户授权清理。清理时在 completion/证据索引中登记已清理的资料类别与时间。视图保留原确认结论，原始附件标为“已清理”，不显示可用下载链接。覆盖率可展示保存的工具统计摘要并标明“原始数据已清理，无法复算”；已有各范围的工具摘要可按范围切换，缺少的范围明确不可计算，不能用百分比反推或手算补数。需要新范围或新证据时重新执行，产生新的运行时间、版本和证据，不能把重跑冒充旧证据恢复。删除 local 之后，历史查看也不要求恢复 knowledge 读取凭证或激活 current.json。


## 验收测试 ID 与范围版本

- ID 使用稳定 `AT-` 前缀，例如 `AT-20261017-a7f3`；`knowledge` 是固定保留目录名，不是验收 ID。
- 用户已指定 ID 时复用；尚无 ID 的新验收由宿主生成一次日期加随机后缀并登记，不要求用户手工编 ID。
- ID 标识一次验收工作，可关联一个或多个 PR、提交、需求。增加/减少范围、重新提交代码、补测、修复、重开阶段都不改变 ID。
- PR/head、组件提交、工具版本、范围版本和阶段尝试是该 ID 下的独立记录。不可将内部尝试编号当作新的验收 ID。
- 用 `scope` 命令追加范围快照，保存真实决定依据；旧快照通过哈希链保留。范围改变使依赖旧范围的后续工作失效，须新建受影响的冻结尝试；旧执行事实和结论来源保留。新增范围不继承原通过，验收期间移出范围不能抹去旧结论和证据；结束后原始数据按清理规约处理。
- 稳定场景 ID 标识同一个业务测试点，可跨验收引用。条件/预期有实质变化时保留其定义版本，不凭相似标题合并。正式用例路径和同一场景的执行次数不改变场景 ID。
- 不同验收写各自 AT 目录；当前验收 ID 只保存在个人本机的 `.acceptance-local/current.json`，不提交、不让各 PR 共同修改。没有跨验收混写的全局结果 JSON。公共 `knowledge` 的同一文件有实际冲突时正常解决 Git 冲突，不能最后写入者覆盖。范围与执行产物不以变动的提交号命名顶层身份。

初始化顺序：把首次 scope 输入放在项目内尚未登记为 AT 的位置或外部临时文件，先调用 `init`，成功后再在返回的本 ID local 目录内建立 workflows。`init` 拒绝已有同 ID 目录；不要预建 workspace/bootstrap 后覆盖指针。需要开始下一项时先保存上一项真实结束结论、核对执行已停止，再 `finish`，随后 `init` 新 ID；旧项缺少结束依据不能自动结束。

初始化和范围变更：

```sh
python3 <skill>/scripts/acceptance_store.py init <项目目录> AT-<ID> --title '<验收名称>' --owner '<负责人>' --scope scope-input.json --basis '<真实用户决定引用>'
python3 <skill>/scripts/acceptance_store.py scope <项目目录> AT-<ID> --scope next-scope.json --basis '<范围变更的真实依据>'
```

范围输入是非空 JSON 对象，记录具体 targets、需求、排除、用户决定及其引用；目标可混合 PR/commit/requirement 类型。验收身份清单不记录绝对机器路径；本机工作路径放入忽略的执行配置。后续归档提交与实际被测提交必须区分，不因提交归档资料而改写旧收据的被测版本。

## 当前验收指针与启动恢复结束

同一项目、同一人只进行一项验收。项目根目录固定使用用户的个人项目工作目录；隔离工作树沿用登记项目根目录的指针，不另开一份当前状态。不同人使用各自的个人项目工作目录。不要建立对话 ID、聊天文件或会话到验收的映射。

登记前核对用户项目工作目录与实际源码 checkout，二者可以不同；不能因 checkout 是 Git 根目录就把验收资料根目录改到隔离工作树。用户工作目录可包含多个源码仓库，验收目录和当前指针仍在该工作目录根部。配置分别记录 acceptance.project_root 与 source_checkout；源码、原收据和冻结记录继续保留真实执行路径。

程序在 init/start/finish/current、知识读取、结构校验、执行 guard 和项目视图入口统一检查资料根目录：如果任一祖先目录已有 `.acceptance` 或 `.acceptance-local`，拒绝在子目录另建或读取独立资料；报错给出已登记的用户项目根目录。Git linked worktree（`.git` 指向含 `commondir` 的工作树元数据）也不能作为资料根目录，必须分别提供用户项目目录和 source_checkout。拒绝发生在创建 current.lock、目录或执行命令之前；不能把错误目录返回成“没有当前验收”，从而误建新 ID。检查不递归扫描工作树、不自动搬迁资料，也不绑定对话。路径名称不是识别依据；普通子源码仓库、子模块或独立临时克隆不能仅凭名称被认定为用户项目，仍须先核对用户任务上下文。程序无法推断尚未登记且无 Git 工作树标记的目录是否符合用户意图。

`.acceptance-local/current.json` 内容只有：

```json
{"acceptance_id":"AT-20261017-a7f3"}
```

**启动/恢复的第一步**是从项目目录读取指针，再读取该 ID 的身份、范围、流程状态和冻结配置；新开对话也走此入口，不能从最新文件时间、某份配置或网页选中项猜当前 ID。

```sh
python3 <skill>/scripts/acceptance_store.py current <项目目录>
python3 <skill>/scripts/acceptance_store.py start <项目目录> AT-<已有ID>
python3 <skill>/scripts/acceptance_store.py read-knowledge <项目目录> --paths workflows/INDEX.md
python3 <skill>/scripts/acceptance_store.py finish <项目目录> AT-<当前ID>
```

- `current` 只读；没有进行中验收返回 `acceptance_id:null`，不创建指针、不选择最近历史。
- 新验收用 `init` 登记并写入指针；接续已有验收用 `start`。指针已经指向同一 ID 时 `start` 幂等；指向其他 ID 时两者均拒绝，不创建另一项验收或静默覆盖。需要换验收时先确认前一项确已结束，再 `finish`，然后 `init/start`。
- 启动、恢复及执行/阶段交接前，公共 guard 读取指针并核对配置 `acceptance.id`。缺失、损坏、目标不存在或 ID 不匹配均停止，不执行项目命令，不自动激活配置中的 ID，不改业务结果。知识读取也按当前指针确定 ID；显式给出 ID 时必须匹配。
- 范围或提交变化不改变当前 ID；依赖版本仍按既有冻结/哈希规约核对。程序中断、错误、等待修复、单场景完成或本批次结束都保留指针，供下次恢复。
- **整项验收结束时**，宿主先保存实际结论、未完成范围和必要证据，确认相关执行已结束，再调用 `finish`。它核对预期 ID，只删除 `current.json`；不删除历史、配置、证据，不把任何场景改成通过。不能因流程停住或关闭对话自动清除指针，也不能在另一个验收已经启动后清除其指针。
- `current.lock` 仅对 init/start/finish 写入加锁，防止两个启动过程同时占用不同 ID；文件本身存在不代表验收进行中。指针写入采用原子替换，失败时不会发布半个 JSON。
- 查看历史、检查归档完整性和视图下拉切换不要求激活历史 ID，也绝不修改当前指针。历史结论修正/资料归档本身不等于重新开始执行业务测试。

指针缺失时，新对话应依据用户任务决定初始化新验收还是显式接续已有验收；没有唯一依据再澄清，不另造对话绑定。此约定只确定当前验收身份，不能跳过原有进程存活检查、不确定执行收尾和恢复门禁。

## knowledge 分层索引

每个有内容的目录必须有 `INDEX.md`，至少包含非空 `## 职责`、`## 何时读取` 两节，说明存什么、适用条件和如何选择入口。用 Markdown 链接登记该目录的每个直接文件和每个子目录的 `INDEX.md`；每条入口补充用途、适用条件、验证状态和必要的阅读顺序。可继续逐层细分，不从根索引跳过中间目录直接链接深层资产。

```markdown
## 职责
项目复用的环境检查脚本与调用约定。

## 何时读取
准备本地测试环境或排查启动问题时读取。

## 内容入口
- [环境检查](check-env.py) — 准备环境时使用；仅本地读取；已验证，来源 AT-xxx。
- [故障流程](recovery/INDEX.md) — 服务启动失败时继续读取。
- [项目现有夹具](project:e2e/fixtures/server.ts) — 使用服务夹具前读取；沿用项目原文件。
```

本地链接使用无标题后缀的简单 Markdown 路径（有空格可用 `<路径>`），子目录入口为 `child/INDEX.md`。`project:` 表示项目根目录中的既有文件，只引用不复制；程序也校验该文件和哈希。HTTP 链接可作参考，但不能代替本地目录索引。禁止路径越界和知识资产符号链接。

脚本必须有对应说明，记录依赖、输入输出、实际命令、副作用、隔离/清理要求和限制。经验标明来源验收、验证状态、适用版本或条件、替代关系。不得把一次成功推广为所有项目的业务规则；过期信息保留明确替代入口。知识脚本不会因为进入索引而自动执行，执行仍受当前任务授权和阶段边界约束。

知识脚本的运行输出、依赖缓存和临时环境写入本验收的 `.acceptance-local`，不在共享知识目录里混入运行产物。Git 项目除检查忽略规则，还检查该目录实际被忽略且没有已跟踪文件，防止只加了 `.gitignore` 却仍将本机资料提交。

项目运行环境和覆盖率准备遵循同一分层：跨验收可复用的安装步骤、测试入口、适配脚本及适用版本写入分层知识索引或项目既有测试树；实际解释器、依赖、工具安装、机器路径、探针和执行收据属于当前 `.acceptance-local/<ID>`。新验收须先读取相应知识，再建立并验证自己的运行环境；旧 ID 的绝对路径和通过凭证不能直接成为新 ID 的准备结果。运行环境依赖项目版本、锁文件、平台和测试入口；它在本 ID 内可供场景顺序复用，业务数据库、用户目录等可变状态仍按场景新建。

**读取规约：**每次启动、恢复及范围变化先读根索引，按适用条件逐层选择并读相关内容；不要只依赖上次对话记忆。用以下入口实际读取文件并生成独立哈希凭证，将输出 `contents` 作为项目操作参考提供给执行 Agent；不将经验当作业务合同：

```sh
python3 <skill>/scripts/acceptance_store.py read-knowledge <项目目录> AT-<ID> --paths workflows/INDEX.md scripts/check-env.py
```

输出中的 `acceptance` 对象原样放入准备 spec、分析/逆向/场景 request、case template 和 plan。它包含项目根目录、稳定 ID、范围哈希和读取凭证路径；交接保持身份/范围一致。只读总索引也可不传 `--paths`，但操作者仍须按索引条件选择适用内容。

**更新规约：**新增/移动/替换资产同步更新本层索引，新增目录同步更新父级索引。知识完成更新前运行 `check`；不能先报完成、再等后续验收偶然发现。程序逐层检查遗漏入口、断链、缺索引、越界，并对知识资产及项目引用建立完整内容哈希；新增或更新任何资产都会使旧读取凭证失效。阶段入口及 v4 阶段交接重新检查；失效即停止在工具准备问题，不改产品结论、不自动重跑。

恢复时需要刷新知识凭证而冻结配置不能改写，可先重新读取，再通过 `ACCEPTANCE_KNOWLEDGE_RECEIPT=<新凭证绝对路径>` 提供新凭证；只允许同项目、同 ID、同范围，旧凭证仍保留。若新知识改变了实际方法/命令/用例而非只是重新读取，仍须新建受影响的冻结尝试。程序能验证文件可发现、已读取和版本一致，不能证明 AI 已理解语义或所选经验足够；不得把结构检查称为独立复审。

## 正式用例与程序门禁

正式用例、配置、测试助手和 fixture 使用项目现有目录、框架、命名、命令和 CI 入口。验收过程在隔离工作树中修改的用例，尚未融合/提交之前只能标为验收候选用例，不能因为场景通过就宣称已进入项目回归体系。融合时保留最终已确认版本及来源，复用项目夹具；普通回归和验收引用同一实现。覆盖率通过框架/运行时适配器接入，不另造一套 Skill 专用用例副本；真实加额等副作用必须由专门显式开关隔离，不能进入默认批量回归。

v3/v4 的公开模型流程入口及 portable CLI、v4 准备/绑定/计划/单场景入口强制要求 `acceptance`，输出必须位于 `.acceptance-local/<ID>/workflows/<attempt>`。工作树固定为本验收根部的 `workspace`，所有场景复用；其来源必须属于登记项目或同一 Git 公共库。正式 `test_roots` 不得是整个项目根目录或验收产物目录。绑定时核对场景 request、catalog、模板属于同一验收/范围，不能跨 ID 误复用证据；共享准备可通过重新建立绑定复用实际能力，不能直接冒用旧绑定。低层工具不是绕过工作流门禁的独立验收入口。

```sh
python3 <skill>/scripts/acceptance_store.py check <项目目录> AT-<ID>
python3 <skill>/scripts/acceptance_store.py guard frozen-config.json --output <新阶段目录>
```

`tests.json` 可选结构为 `{"items":[{"path":"e2e/example.spec.ts","command":["项目已有测试命令"],"scenario_ids":["稳定场景ID"]}]}`。校验路径存在、未放入验收目录，并记录可批量调用的命令。程序不因场景 passed 自动认证用例语义或改写 CI；完成状态须分别说明场景结论、正式用例融合和证据归档。

## 完整场景清单与提交证据

`scenarios.json` 使用 `acceptance-catalog-v1`，包含 `project` 对象（例如 `{"id":"stable-project-id","label":"Project","revision":"frozen revision","root":"/absolute/source"}`，不能仅传名称字符串）、完整 `requirements` 数组、`reverse_rules` 数组、全部 `scenarios` 数组（包含未执行）。可用额外 `scope_scene_ids` 说明本验收选中部分，不能用它替换项目分母。每场景至少有稳定 `id`、`requirement_id`、`title`、`description`、`priority`。发布和读取使用同一结构校验；非法项目对象在写入目录或历史前被拒绝。发布保留旧清单版本，重复 ID、无主需求/规则或待确认规则下的可执行场景被拒绝：

```sh
python3 <skill>/scripts/acceptance_store.py catalog <项目目录> AT-<ID> --input complete-catalog.json
python3 <skill>/scripts/acceptance_store.py archive <项目目录> AT-<ID> --source <本验收阶段目录> --files trace.json execution.json review.json evidence.log --basis '<已筛选脱敏、需要共享的依据>'
```

归档记录请求的原来源及文件时间；视图按来源去重同一工作流，优先完整本机实例，其次选择配套文件更完整的归档。部分 v4 元数据归档不能借复制时间覆盖已完成尝试。v4 完整结果以 `--v4-result` 固定协议选项按 [v4 规约](portable-workflow-v4.md#覆盖率与实时视图) 自动选择当前实际执行/独立复审的绑定文件，可复算覆盖率使用[项目覆盖率归档配置](project-coverage-protocol.md#归档与展示验证)的 `--v4-scene` 自动跟随最终复审一并发布，独立补采使用 `--coverage-report`；其他额外证据仍以 `--files` 选择；不要手写新判定或修改旧 JSON 来适应视图。

归档仅复制显式文件清单或调用者明确选择的固定 v4 结果协议文件，不递归打包工作树、原始环境或全部 Agent 会话；用户授权分享的前提不由此命令补足。冻结文件字节保持不变，`record.json` 保存路径映射和文件哈希，使迁移后的视图能找到随包证据。覆盖率若依赖未归档的原始数据/源码/工具配置，明确不可复算；不凭摘要恢复命中，不把其他版本计数加进来。

## 一个项目入口，按验收 ID 切换视图

```sh
python3 <skill>/scripts/v3/serve.py <项目目录> --acceptance-id AT-<ID> --port 0
```

视图只读发现该项目 `.acceptance/AT-*/manifest.json`，下拉选择历史或当前验收。未指定浏览对象时优先显示 `current.json` 指向的验收；没有进行中验收时可以浏览最新历史，但明确显示“当前无进行中的验收”，不创建指针。浏览选择保存在浏览器 URL `acceptance_id`，与当前执行 ID 分别显示，任何查看、切换、刷新均不写 `current.json`，不同人/标签页不互相改执行状态。只读取所选 ID 的提交记录、本机 workflows 和完整场景清单，显示需求/规则 → 场景 → 用例/操作 → 执行 → 独立结论 → 覆盖率；不扫描隔离 checkout、依赖或其他验收目录。切换 ID 时整组更新概览、进度、追踪、证据与覆盖率，清空旧数据并丢弃过期响应，不能瞬间把前一个验收的计数挂到新 ID。

项目场景指标仍以所选验收保存的**项目完整清单**为分母；结果与执行历史从该 ID 的记录取，不自动借用其他 ID 的通过结论。跨验收复用正式用例/知识不等于复用结论；需要引用既有执行证据时必须显式绑定其真实来源、范围和版本。同一 ID 内保留执行过事实和最近已确认结论；结果类别合计等于已执行数。缺清单或清单漏掉已发现场景时，展示明细与缺口，但不把已发现子集当作项目比例。

覆盖率只按所选 ID 的真实兼容报告，由专用工具汇总，项目/修改文件/修改行切换同步更新行和分支。同一 ID 可有多个被测版本，不能跨版本合并；每组数据注明实际版本与工具，不得求平均变成一个“总覆盖率”。历史验收不因当前 knowledge 更新而重测，也不因切换界面发生执行。不可读取的本机/外部证据如实提示，不能假装已随 Git 提交。

已有旧目录不自动改名、复制或伪造 ID。迁移时先明确其归属与完整清单，再登记并显式筛选归档，保留旧原件。临时只读查看旧目录可用 `serve.py --legacy-assets <旧产物目录> [...]`；这是历史查看入口，不允许用来继续新流程或冒充已完成新组织迁移。


## 真实旧资料迁移规约

迁移必须由用户明确授权，并延续原验收范围。先冻结原视图/结果清单、完整项目场景目录、最近已确认结论及其出处，再创建一个稳定 ID 和当前指针。迁移结束是资料维护完成，不表示整项验收结束；用户要求继续当前验收时保留 current.json。

实践表明，旧产物不能直接塞进新 workflows 或 records 的自动扫描区域：其中含过期请求、旧失败、已替代复审及不同覆盖率版本，扫描可能使已纠正的结论再次参与排序。旧文件应原字节保存在本机 imports，未来的新执行才进入 workflows；共享 records 放可核验的迁移投影，明确标记 import_source，绑定原快照引用和 JSON 位置。原执行时间、确认时间、版本、用户纠正规则和风险处置保持不变，不用迁移时间冒充最新执行。结构校验不能代替独立复审，迁移不生成新业务判定。

`evidence-index.json` 使用 acceptance-evidence-index-v1，包含 acceptance_id 和 artifacts。每个内容哈希对应 sha256、size、mime、storage（local:相对本验收本机目录路径，或 shared:相对本验收提交目录路径）。同哈希可去重引用。原始环境、会话、数据库和大运行数据只留本机 imports；共享索引不得自动把这些原件打进 Git。原路径映射、复制清单、被排除工作树/依赖的原位置及保留原因放本机清单。可共享的场景追踪、索引、说明、必要脱敏证据归入对应 ID 的共享 records。没有提供本机原始数据的其他工作目录应明确显示证据或覆盖率缺口，不能假装共享索引等于共享了全部证据。

可用 scripts/import_legacy.py 独立复制旧数据并逐文件校验哈希；它不执行旧脚本、不恢复旧进程、不改写配置、不删除源。支持独立写时复制的平台可以节省磁盘空间；禁止以共享可写 inode 的硬链接冒充独立冻结副本。隔离 checkout、Git 元数据、依赖和缓存保留原处并列出排除清单，不复制成项目正式用例。原件、复制件、候选用例快照和正式回归集必须分别说明。旧 config.json 不因复制而具备新流程的 acceptance 绑定，接续工作需创建新的规范配置并引用旧证据，不能直接修改原件或直接重跑。

覆盖率的实际采集版本与业务确认版本分别保存。汇总按 coverage_actual_revision（存在时）分组，并由专用 provider 校验源码、工具和单位兼容，不能按沿用的业务结论版本拆错组，也不能把不同采集版本合并。冻结报告内的绝对路径不改写；可提供 acceptance-path-map-v1 的只读传输映射，让原 provider 读取新目录中已校验同哈希的 prepared、baseline、探测证据、执行收据和原始快照。映射适配器仅转换文件读取路径/目录列举，不识别分支、不改计数、不修改工具实现指纹，并禁止回退读取未映射旧目录。实际统计继续使用对应专用工具；映射、数据或工具不匹配时明确 unavailable/incomplete。

专用工具汇总可按报告集合、原始依赖状态、范围清单、路径映射与工具实现哈希缓存；增加场景、数据变化或范围变化必须使缓存失效。范围切换使用同一兼容输入由工具生成的全部范围结果，概览和场景行同步显示相应范围的行/分支值；不自己加数或平均百分比。

多个视图标签页同时刷新时，同一份冷数据只允许一次专用工具汇总，其余请求复用验证后的结果。只读视图可按已登记文件状态缓存结构校验和快照；场景记录、证据、索引、范围、当前指针、知识或工具变化必须失效，活动中的工作流还需刷新进程状态。该缓存不得替代执行前完整检查，不递归扫描大型 imports 原件树。页面应展示加载或读取错误，避免空白页面被误当成无验收数据。

迁移交付前核对：完整场景 ID/需求原文一致；每个已执行场景的最近确认状态、时间、实际版本及用户纠正依据一致；互斥分类合计等于已执行；所有视图证据引用可读取且哈希匹配；使用新目录数据通过专用工具汇总的各范围值与原报告一致；当前指针未被浏览切换改写；原证据和产品源码未修改。保存迁移审计报告。仅资料校验和工具自检，不隐含重跑业务测试或新独立复审。
