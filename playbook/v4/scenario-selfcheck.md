在同一次任务内完成生成与审查，最终只提交一次完整场景 JSON。不要输出中间清单或审查文本。提交前按以下顺序在内部执行，并在发现问题后直接改写草稿：

1. 从目标需求原文抽取每项独立可观察的验收义务；只把共享约束和相关需求中直接决定本需求输入或预期的内容纳入。特别核对正常路径、拒绝条件、状态转换、已持有资源、进行中的记录、历史数据与恢复约束。不要把相关需求的独立功能移入本需求。
2. 为每项义务找到至少一个能区分正确与错误实现的场景判据。对于“保留”“不重置”“兼容迁移”等义务，逐一考虑输入明确提到的不同持久状态和资源，并核对操作前后，而不是只检查最终页面或一个已完成状态。相同目的可以合并输入组，合并时要写清各组的预期。
3. 假设一个实现想侥幸通过整份场景列表：它能否只在某个未覆盖的状态、入口、数据阶段或边界上违反原文？若能，补充输入组合或场景。再检查场景间是否重复、是否超出目标范围。
4. 逐项核对预期的依据。若原文及已确认合同没有确定某种状态转换或数据选择规则，不得写成任意一种结果都算通过，也不得从当前实现猜测结果；只能断言已确定的不变量，并在 change_summary 中简短标出尚待确认的判据。不要把无法判定的预期交给用例阶段。
5. 最后结合全部需求与整体业务目标，对完整场景列表统一评级。P0须直接验证主要业务闭环或有依据的重大风险；不要把核心路径拆散后因为单个步骤看起来较小就全部降级，也不要因同属核心模块、都是原文“必须”或都会降低可靠性而把所有拒绝/边界场景升级。逐条问候选 P0 相比正常主路径有什么独有重大后果，并检查相似失败后果的等级是否一致。不为凑数量升降级。

这只是同一 Agent 的内部自审，不声称存在另一位独立审查者；最终输出仍严格遵守原 JSON 格式。
