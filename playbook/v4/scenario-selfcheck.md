在同一次任务内完成生成与审查，最终只提交一次完整场景 JSON。不要输出中间清单或审查文本。提交前按以下顺序在内部执行，并在发现问题后直接改写草稿：

1. 从目标需求原文抽取每项独立可观察的验收义务；只把共享约束和相关需求中直接决定本需求输入或预期的内容纳入。特别核对正常路径、拒绝条件、状态转换、已持有资源、进行中的记录、历史数据与恢复约束。不要把相关需求的独立功能移入本需求。
2. 为每项义务找到至少一个能区分正确与错误实现的场景判据，并指出每条场景相对普通成功路径的区分条件和主要针对的错误实现。对于“保留”“不重置”“兼容迁移”等义务，逐一考虑输入明确提到的不同持久状态和资源，并核对操作前后，而不是只检查最终页面或一个已完成状态。相同错误机理与失败后果可以合并代表输入，合并时要写清各组的预期；普通路径与特殊分支若验证不同错误、失败影响也不同，拆开后分别评级。若 P0 中有特殊代表输入，判断移去它后是否仍能证明普通主路径；能则让普通输入留在 P0、特殊输入按自身后果另评，除非特殊输入本身构成有依据的重大风险。
3. 假设一个实现想侥幸通过当前需求的整份场景列表：它能否只在某个未覆盖的状态、入口、数据阶段或边界上违反原文？特别反问：它若拒绝原文允许的一类特殊有效输入，普通成功场景仍会通过吗？若会，保留适当等级的有效输入场景，不要只补非法输入拒绝。再逐条反问删除此场景后，是否仍有别的场景证明同一错误机理及后果；若是，合并或删去实质重复，同时保留不同义务独有的断言。把相关需求可能生成的场景作为对照：本需求是否又建立了同一条件、同一动作和同一预期的完整场景？若是，只留下本需求独有的判据，把共用条件当作准备数据；不要让每个相关需求各自重测一遍同一输入域。核对超大输入、长时间运行或大量状态组合是否确有独有判别价值，能否用更小的合规代表输入证明同一错误；保留必要的大规模验证时，按实际重要度评级，不因数值很大自动升降级。再检查是否把相关需求的独立功能纳入本需求，或出现相互矛盾的预期。
4. 逐项核对预期的依据。若原文及已确认合同没有确定某种状态转换或数据选择规则，不得写成任意一种结果都算通过，也不得从当前实现猜测结果；只能断言已确定的不变量，并在 change_summary 中简短标出尚待确认的判据。不要把无法判定的预期交给用例阶段。
5. 最后结合全部需求与整体业务目标，对当前需求的完整场景组逐条评级。P0 须直接验证主要业务闭环或有依据的重大风险；逐条假设仅本场景的区分条件失败、其余场景通过，核对通常条件下的主要目的是否仍可完成。若仍可完成，只能凭本场景特有且具体的重大风险保留 P0，不能把特殊条件或收尾要求称作“正常闭环”来替代后果说明。重大风险理由要能由场景失败直接证明；不能因设想它还可能破坏所有数据就升级。比较同一目标及相关目标中性质相同的数据损失，检查入口差别是否真的改变损害范围；若同一能力的两个场景分别验证通常成功与资源竞争、冲突或失效，核对哪一个真正能造成更大业务损失，不要把较轻的前者评得高于较重的后者。不要把核心路径拆散后因为单个步骤看起来较小就全部降级，也不要因同属核心模块、都是原文“必须”或都会降低可靠性而把所有拒绝/边界场景升级。对 P1、P2、P3 也逐条核对具体影响与已确认的替代方式；用户合理会遇到且原文要求拒绝并给出反馈的特殊输入，不能只凭普通成功路径仍可用就自动归为 P2。不要把所有非 P0 场景笼统放进 P1。逐条问等级理由是否只解释了场景中的一部分判据，是否与相似失败后果的场景一致；若不一致，先调整场景边界或理由。不为凑数量升降级，也不要求本需求覆盖每个等级。

这只是同一 Agent 的内部自审，不声称存在另一位独立审查者；最终输出仍严格遵守原 JSON 格式。
