# 单目标场景规则

原始需求保持原文和稳定 ID。每次只为一个需求或一条已支持的逆向规则生成自己的场景；全部需求、整体目标和分组用于理解依赖及重要度，相关需求不因此获得场景归属。用户排除项和待确认合同不能被偷偷纳入必测范围。白盒仅使用已冻结的逆向规则及源码依据；实现本身不构成业务预期。

一个场景是一项可判别的验收目的，写清适用条件、必要操作和预期结果，可合并同一目的的代表输入。不同错误机理和重大风险可独立成场景；不能用笼统的“流程正确”代替具体结果，也不能仅按值或状态做重复组合。覆盖目标原文的正常路径、拒绝条件、状态变化、已有数据保留及必要边界；不加入与目标几乎无关的邻近功能。具体用例步骤、命令和证据留待执行阶段。

预期必须有原始需求、已确认相关需求或独立合同依据。未知选择规则、跨来源比较、未确认数据合同等保持待确认；不要从当前代码猜预期。生成后内部检查遗漏、重叠、范围外内容和不可判定的结果，并直接修正最终列表。

区分业务义务与证明方法：测试可以选择极端输入或不同运行条件来暴露原文违约，但不能借此新增输入交互策略、额外字段处理方式、同步时机、输出字段或展示格式。用户确认原始需求不等于确认后来生成的附加策略。自审时比较两种都可能满足原文的实现；若仅因未约定的实现选择而一方被场景拒绝，收敛到原文已确定的不变量，并在 change_summary 保留待确认边界。场景自己的文字不能反过来成为其预期的独立依据。

结合全部需求和整体业务目标统一评级。P0 直接验证主要正常业务闭环或有独立依据的重大风险；可修复、回滚或调配置不自动降级。**某项是需求的必要验收条件，不代表它本身是 P0。** 对每条候选 P0，分别问：它主要验证的失败是否会破坏主要路径或造成重大风险？若它主要验证某类无效输入、保护分支或局部边界，而有效主路径仍可完成且没有重大后果依据，按其实际影响评 P1/P2；不要因为它“涉及核心模块”或“可能使证据不可靠”就自动沿用主要路径的 P0。跨用户/跨来源错误只有在确有严重业务后果依据时才提升，不凭空推定隐私泄露或全局影响。P1 为重要分支或显著影响，P2 为较低影响，P3 为轻微体验；不按固定数量或比例凑等级。相似失败后果应有一致等级，等级理由具体说明场景独有的失败影响。内部自审不声称另一位独立 Reviewer 已审查。
