# 默认生成流程：先复用，再补缺口

本契约适用于 `implement`，在原有同一连续会话内完成，不默认串行启动完整查找 Agent。不增加独立评估循环或产品判定规则。已有用例足以验证场景时允许零修改，不能为了表现工作量新增测试。

## 操作顺序

1. 按共同查找标准定位当前场景的已有测试，阅读实际条件、操作、断言、参数、helper 和替身边界。先使用公共准备和已有有效查找记录，不重复准备项目。
2. **修改测试或运行调试之前**，把真实已有测试结果按 `existing-case-discovery-v1` 写入指定 checkpoint 请求文件，并调用宿主给出的 `checkpoint` 入口。请求包含 `test_files`、`case_descriptions`、`case_discovery`；字段与已有查找契约一致，引用启动时原文。无关联时列表为空，仍保留场景目标和实际检索范围。它只是本会话的一次确定性存档，不启动另一个模型。
3. checkpoint 成功后，按各目标的现有支持决定直接复用、补充现有测试或新增测试。先明确仍缺少的条件、操作、结果核验及会放过的错误，再做必要修改。只缺一个断言时优先补现有测试；新增项应针对独立的必要缺口，不复制已经足够的覆盖。必要的隔离或运行困难可以成为另建测试的原因，但必须说明；不能仅因标题不友好就重写测试。
4. 按原统一入口调试最终用例组。最终 `case_descriptions` 包含本场景实际采用的复用项和新增项，保留已有原代码标题和来源。新文件不是“新增用例”的唯一判断：在旧文件中新增一个业务测试项也标 `generated`；补已有测试仍标 `existing`。
5. 在原 JSON 中增加 `case_reuse`。它说明选择与新增的依据，不构成独立设计评估或执行结论。结构/引用核验不等于语义已被证明；独立评估仍阅读最终实际用例组。

已有测试充分支持场景且没有已证实的执行或证据问题时，直接复用并保持测试及辅助代码不变。当前场景没有提到某个已有断言，不代表它错误：它可能服务于其他需求，不得据此删除、放宽或替换已有断言，也不能把这种修改称为“补缺口”。本次新增断言才需要避免从当前实现习惯推导额外预期。确有独立合同证据证明旧断言错误时，记录该证据和影响，最小修正并保留其他需求的支持；合同未明则披露疑问。不要为标题、文案匹配偏好、日志美化、增加无要求的输入变化或顺便整理清理代码而改写已可用测试。真实隔离、清理或证据问题必须先给出具体依据，再决定必要修补。

```json
{
  "case_reuse": {
    "schema": "case-reuse-plan-v1",
    "decisions": [{
      "case_id": "最终case_descriptions中的ID",
      "action": "reuse|extend|new",
      "existing_case_ids": ["checkpoint中的已有用例ID"],
      "obligation_ids": ["checkpoint中的场景目标ID"],
      "reason": "直接复用的贡献，或必须补充的具体缺口；为什么现有项不能充分承担"
    }],
    "not_selected": [{"case_id":"checkpoint中找到但最终未采用的ID", "reason":"重复贡献、无法运行或不适用等具体原因"}],
    "limitations": ["未查明的范围与未验证部分"]
  }
}
```

每个最终业务测试项恰有一条 decision。`reuse`、`extend` 必须指向已有用例及相同的真实文件和声明标识；`reuse` 保留被引用的原测试正文不变；`extend` 对已存在的测试补断言或必要辅助能力。`new` 不得伪装为复用，`existing_case_ids` 为空且最终来源为 `generated`。目标只来自当前场景，不引入相邻需求。已有项可以支撑多个目标，多个互补项可以共同承担一个目标。

`not_selected.case_id` 只引用冻结 checkpoint 的 `discovery.case_descriptions[].id`（与 `existing_case_ids` 使用同一个 ID 集合）；它不引用文件名，也不引用 `case_discovery.excluded_candidates`。已排除候选的理由已在 checkpoint 保存，不再复制到 `not_selected`。若检查点只有 C1 且最终直接复用 C1，则 `not_selected` 必须为 `[]`。提交前从 record_path 读取实际 ID 集合，核对 selected 与 not_selected 恰好覆盖该集合且互不重叠。

找到但未采用的项必须解释，不因选择少量新项悄悄丢掉已有支持。跳过或条件启用的真实测试仍记录为已有支持，其当前可运行性与验证边界单独说明，不能借此声称未找到。最终无法就绪时可以没有 decisions，须保留 checkpoint 和具体原因；不能称已完成场景测试。

## 搜索结果复用与升级

已有查找回答可以直接用作 checkpoint 请求的候选内容；checkpoint 会重新核对当前场景原文、启动时文件字节和实际引用。失配时重新定位受影响部分，不信任过期缓存。一般场景在本会话完成定向搜索；只有调用方判断大型多组件项目的检索工作值得单独分担时，才先运行静态查找，并把已验证结果交给实现会话。不要在生成前默认运行含本地调试的完整查找流程。

## 宿主存档

宿主在会话启动时只记录 Git 索引和文件集合；干净的已跟踪文件按 Git 对象延迟读取，已有未提交/未跟踪文件保存原始字节。不为所有干净源码额外做全仓内容哈希。

checkpoint 核对被引用的原文件并保存 `case-reuse-discovery.json` 及选定原文快照；最终核对复用身份、声明范围、目标双向引用和决策列表，另存绑定最终回答的 `case-reuse.json`。原 `answer.json` 不重写。存档属于该场景的用例准备记录，不是正式执行凭证；差量修复后的最终代码仍由原独立评估和执行复审核对，不把早期复用计划当成修复后仍充分的证明。

宿主在复用检查完成后按 [用例 ID 合同](case-display-contract.md#永久用例-id关联后由宿主统一落地)添加普通 ID 注释。该精确注释补丁不改变 reuse 的业务正文；复用报告随后绑定最终结果哈希。Agent 保留已有标记，新测试不复制别人的 ID。

若原生结构化提交仍只漏掉固定的 `case_reuse.schema`，宿主可沿用原 Case 会话请求一次模型结构补正：禁止非提交工具、禁止重跑，原答另存，且比较完整 JSON 值只允许补上该固定标记。任何业务内容变化、再次遗漏或补正失败均拒绝；不适用于缺少用例、观察、引用、选择理由等实质内容。

提交前可将完整候选对象写到宿主给定 `final_request_path`，调用 `final_check` 并追加此路径。它在当前租约下只读执行最终相同的结构、身份和源码引用检查，不写入 answer 或确认结论；按错误修正候选后原样提交，宿主仍再次校验。`source.title` 使用引用行段中连续出现的声明名，不把类名与方法名拼成源码中未出现的限定字符串。

只读最终预检也检查源码注释条件：即使用例 origin 为 existing，实际声明前尚无永久 ID 时，仍须在 source.id_comment 提供项目语言可用的安全模板（例如 Python 使用 `# {id}`，由宿主填入完整标记）。预检不生成 ID、不插入注释，最终身份登记仍由宿主完成。
