# 宿主意图与工作流输入

宿主理解完整用户请求，选择公开入口及调用范围。
工作流从领域目标和项目事实开始，自行完成内部发现、执行、修复及结果记录，不继承宿主整段对话。

| 信息 | 归属及交接 |
| --- | --- |
| 完整交付流程、先做哪个需求、只执行一个场景 | 宿主选择和组合调用；向场景／执行入口提供真正需要的目标 ID。 |
| 观察每步时间、诊断后先不修改 Skill 实现 | 宿主记录和实现修改边界；不成为覆盖率环境内部禁止修复的指令。 |
| 产品需求、判据、必要背景原文与来源 | 冻结后传给需要这些判据的分析、设计、用例及复审角色。 |
| 项目位置、用户指定的实际启动命令和子进程关系 | 交给覆盖率准备等需要这些事实的工作流；项目中可发现的信息由工作流检查。 |
| 覆盖率准备中的适配器错误、安装问题及程序核验失败 | 工作流内部诊断、修复并重新验证；保存实际过程，交付可用环境或明确不能支持的原因。 |

覆盖率准备不需要业务场景数量或产品通过目标。
没有需求或场景时，也可以单独为项目准备覆盖率环境，工作流不为此虚构业务需求。
宿主选择的最少输入和工作流内部形成的详细运行资料是两个层次，后者由工作流负责。

## 跨工作流接续

主 Agent 对用户授权的最终目标负责，独立工作流对自己的一次业务操作负责。
工作流返回 `blocked` 后，宿主先读具体原因、原答和真实执行收据，再决定后续调用；`completed` 仅表示调用结束，仍须检查 `review_status` 等业务结果，`repair_required` 不等于验收通过。
不把这些可修复结果都当作整个任务终点，也不将用户只要求创建／冻结等明确停止点扩成完整验收。

| 实际诊断 | 宿主后续调用 |
| --- | --- |
| 测试／证据缺口 | 将具体诊断交回用例准备或正式执行所支持的修补过程，保留相同场景和已有永久 TC。 |
| 已就绪环境遗漏实际执行器、依赖或进程采集路径 | 把实际命令、cwd、执行器及进程关系、失败资料交回 runtime／coverage-prepare；通过后重新 project 绑定，再继续原用例。 |
| 产品缺陷 | 保留真实失败，继续本次范围需要的独立判断和报告；不以准备修复授权推导出产品修复授权。 |
| 运行中、未知副作用或遗留场景归属 | 先通过 recover 检查进程和已发生效果；核实后采用已完成资料或显式 supersede 保留旧尝试并释放归属，不能删锁重跑。 |
| 实际缺少认证／授权／必要输入、调用资源耗尽或已证实无法支持 | 说明具体原因、已完成范围和可继续条件，不循环重发相同失败请求。 |

准备记录中的 `ready` 对应当时实际验证的执行路径，不代替新出现路径的验证。
覆盖率在用例调试中漏采产品子进程时，将这条进程事实及旧准备、调试资料交给新的覆盖率准备请求；有完整显式绑定时复用仍有效的 runtime 和源码清单，避免重新安装或重新发现整个项目。
工作流内部负责选择修复方式、生成必要采集代码并验证，宿主不替它编写采集器或为了适应采集器改变业务测试方式。

接续时使用新请求保存改变后的输入和准备资料，旧失败、原始证据和永久 TC 保留。
若只读复用调用完成后发现测试缺口，而只读模式是宿主自行选择、用户允许修补测试，可通过新的可修补用例请求处理明确反馈，再正式重验；用户明确要求不得修改测试时不越过该限制。
若原场景仍持有工作区，先按真实进程与副作用证据恢复／释放归属，再准备和重新绑定；已完成的旧请求重入只会复用旧结果，不能用它表达修复后重跑。
后续调用只携带本次操作所需事实；“推进完整任务、记录耗时”继续由宿主负责，不变成所有角色的全局指令。
继续与否根据实际进展、可修复性、已授权效果和资源判断，不额外增加通用修复次数、命令白名单或项目语言假设。
