在同一次任务内完成生成与自审，最终只提交一次 JSON：简洁场景列表及顶层 selfcheck 核对记录。不要另发中间草稿或假称独立审查。提交前按以下顺序检查，并在发现问题后直接改写草稿：

1. 从目标需求原文抽取每项独立可观察的验收义务；只把共享约束和相关需求中直接决定本需求输入或预期的内容纳入。特别核对正常路径、拒绝条件、状态转换、已持有资源、进行中的记录、历史数据与恢复约束。对每项义务截取目标原文的连续片段并映射到本目标的场景；相关需求若拥有该义务，不得借准备步骤把它写成当前目标的主判据。区分业务判据与项目执行命令：需求已说明操作、输入与期望时，可以设计场景并要求用例准备阶段从项目文档确认启动、状态目录、运行时探针等实际命令；场景生成不需要预先知道具体命令。若即使完成合理的项目准备仍没有可信操作入口或独立可观察判据，则记录具体缺口，不编造产品接口或假装已覆盖。
2. 为每项义务找到至少一个能区分正确与错误实现的场景判据，并指出每条场景相对普通成功路径的区分条件和主要针对的错误实现。对于“保留”“不重置”“兼容迁移”等义务，逐一考虑输入明确提到的不同持久状态和资源，并核对操作前后，而不是只检查最终页面或一个已完成状态。相同错误机理与失败后果可以合并代表输入，合并时要写清各组的预期；普通路径与特殊分支若验证不同错误、失败影响也不同，拆开后分别评级。若 P0 中有特殊代表输入，判断移去它后是否仍能证明普通主路径；能则让普通输入留在 P0、特殊输入按自身后果另评，除非特殊输入本身构成有依据的重大风险。
3. 假设一个实现想侥幸通过当前需求的整份场景列表：它能否只在某个未覆盖的状态、入口、数据阶段或边界上违反原文？特别反问：它若拒绝原文允许的一类特殊有效输入，普通成功场景仍会通过吗？若会，保留适当等级的有效输入场景，不要只补非法输入拒绝。再逐条反问删除此场景后，是否仍有别的场景证明同一错误机理及后果；若是，合并或删去实质重复，同时保留不同义务独有的断言。把相关需求可能生成的场景作为对照：本需求是否又建立了同一条件、同一动作和同一预期的完整场景？若是，只留下本需求独有的判据，把共用条件当作准备数据；不要让每个相关需求各自重测一遍同一输入域。对场景内每次重复操作也做删除检查：去掉后仍能证明同一义务与错误机理的，就缩减为一个可信代表组合；不同义务或独立后果不得为缩短而删去。核对超大输入、长时间运行或大量状态组合是否确有独有判别价值，能否用更小的合规代表输入证明同一错误；保留必要的大规模验证时，按实际重要度评级，不因数值很大自动升降级。再检查是否把相关需求的独立功能纳入本需求，或出现相互矛盾的预期。特别比较较宽目标与明示特殊输入的较窄目标：同一输入、同一操作、同一结果只能由有明确独有判据的目标建场景；普通输入若不能区分较窄目标的独有错误，也不在较窄目标重复建立。仅重复视觉可用性检查不算独有判据。逐项把本场景的代表输入代入其主要错误实现；若正确与错误实现呈现相同结果，该输入不能支撑独立场景，应换有区分力的输入或删除重复场景。
4. 逐项核对预期的依据与独立可观察结果。若原文要求拒绝并反馈，场景中每类被检查的输入都要明确验证拒绝和反馈，不能只写其中一类的反馈。若原文及已确认合同没有确定某种状态转换或数据选择规则，不得写成任意一种结果都算通过，也不得从当前实现猜测结果；只能断言已确定的不变量，并在 change_summary 中简短标出尚待确认的判据。明确允许两种相反结果且未约定共同保护义务的片段，只记录 not_required_reason，不生成任意一方的判定，也不算缺口；若有共同必达不变量，则针对不变量设计场景。把“项目文档中确定启动命令或测试夹具”写成用例准备依赖即可；不得只因输入中未附该命令而放弃可设计的重启、目录隔离或运行时能力场景。找不到可信入口或判据时在 selfcheck 的义务记录中标出 gap_reason，不把无法判定的预期交给用例阶段。若全目标确无可信场景，可输出空场景列表及逐项缺口；该目标保持未充分覆盖状态。
5. 最后结合全部需求与整体业务目标，对当前需求的完整场景组逐条评级。P0 须直接验证主要业务闭环或有依据的重大风险；逐条假设仅本场景的区分条件失败、其余场景通过，核对通常条件下的主要目的是否仍可完成。若仍可完成，只能凭本场景特有且具体的重大风险保留 P0，不能把特殊条件或收尾要求称作“正常闭环”来替代后果说明。重大风险理由要能由场景失败直接证明；不能因设想它还可能破坏所有数据就升级。比较同一目标及相关目标中性质相同的数据损失、重复扣减、权限越界等后果，检查入口差别是否真的改变损害范围；若同一能力的两个场景分别验证通常成功与资源竞争、冲突或失效，核对哪一个真正能造成更大业务损失，不要把较轻的前者评得高于较重的后者。不要把核心路径拆散后因为单个步骤看起来较小就全部降级，也不要因同属核心模块、都是原文“必须”或都会降低可靠性而把所有拒绝/边界场景升级。对 P1、P2、P3 也逐条核对具体影响与已确认的替代方式；用户合理会遇到且原文要求拒绝并给出反馈的特殊输入，不能只凭普通成功路径仍可用就自动归为 P2。不要把所有非 P0 场景笼统放进 P1。逐条问等级理由是否只解释了场景中的一部分判据，是否与相似失败后果的场景一致；若不一致，先调整场景边界或理由。不为凑数量升降级，也不要求本需求覆盖每个等级。把每条场景独有失败及具体后果写入 selfcheck，而不是只在心里比较。

这只是同一 Agent 的内部自审，不声称存在另一位独立审查者；场景对象仍严格遵守原五字段格式，核对记录单独放在顶层 selfcheck。

义务映射的 `scene_ids` 非空时，不提供 `gap_reason` 或 `not_required_reason`；补充取舍说明可写入 `basis`。仅在 `scene_ids` 为空时，在 `gap_reason` 与 `not_required_reason` 中选择一项，避免同时声称同一片段已覆盖和不必覆盖。

另核对目标是否涉及用户可见界面或交互，明确记录 `ui_requirement.required` 与原因。UI 目标的每条场景都须在同一场景描述中同时给出功能结果和可观察的视觉判据，并把描述里的视觉判据原样记录到对应 `scene_check.ui_visual_expectation`。非 UI 目标将其设为空字符串。不要用“截图正常”“页面美观”这种不可核查的泛词；说明关键状态中的内容、控件可见性、遮挡、可读性与可操作性。美观性、装饰布局和设计风格只能来自本次冻结约定；逐项检查共享规则及排除项，删除范围外判据，不把其他验收的偏好当成当前用户要求。已明确纳入的风格要求仍须保留并按其真实依据核对。
