# App delivery acceptance

Requires macOS/Linux, Python 3, Git, Node.js >=22 with npm, and usable authentication/model access for the calling Agent (Codex or Claude Code). Before starting model workflows, the calling Agent explicitly supplies `ACCEPTANCE_AGENT=codex|claude-code` and its actual `ACCEPTANCE_MODEL`; preserve its current provider/authentication environment and, for a selected Codex profile, pass `ACCEPTANCE_CODEX_PROFILE`. Never infer the Agent from installed executables or installation folders, substitute a default model, or fall back to another service. If the current model/configuration cannot be obtained, ask for the missing information before model execution. Run the [Agent runtime preflight](references/agent-runtime.md) once before acceptance analysis; do not record credentials in acceptance artifacts. Internal implementation and independent review remain separate sessions of the selected Agent. A session cannot be resumed using a different Agent, model or service.

Before model workflows or SPEX backfill, run `python3 <skill>/scripts/ensure_runtime.py`. It installs the committed npm lock into `<skill>/playbook/node_modules` on first use and reuses a verified installation afterward; model workflow entrypoints also perform this check automatically. Do not install these packages globally or into the tested project. Use `<skill>/playbook/node_modules/.bin/spex` for default backfill. Dependency preparation does not initialize or modify project SPECs. See [runtime preparation](README.md#使用环境).

Use this Skill to freeze the complete definitions selected for one delivery test, adopt existing scenarios or fill scenario gaps, and execute cases with evidence-based delivery judgments. Preserve the original requirements verbatim and retain their stable IDs. Code-derived rules are separate sources; confirm their intended behavior before treating them as acceptance obligations. A source branch or nearby feature does not by itself expand the user's test scope.

The current route is **v4** for frozen Git projects with locally executable automated tests: v3 whole-list analysis and white-box reverse analysis feed v4 one-target scenario generation, shared project preparation and one-scene implementation/execution/review. The v4 stage runners are single-Agent tasks with deterministic handoffs; only case execution receives a separate independent Reviewer. Use the [v4 operating contract](references/portable-workflow-v4.md) for this route. Keep the [v3 portable route](references/portable-workflow-v3.md) for source-free black-box and actual manual operations; a v4 automated run must never fabricate either. Do not start older acceptance-organization Playbooks or create acceptance-unit ownership.

## Frozen definitions and Agent-owned source interpretation

Projects express agreements in many forms. The Agent reads and understands the actual sources, chooses the admitted scope, preserves original text and provenance, judges semantic changes and their impacts, and performs optional backfill only within user authorization. Do not add project SPEC parsers, source-type adapters, online synchronization or mandatory backfill to this generic Skill.

For authorized backfill, reuse the project's existing agreement conventions. If the Agent confirms that no applicable convention exists, use the actual SPEX scaffold tool to initialize the project's default SPEC organization at that point, then follow its generated rules. Do not initialize SPECs merely to begin testing a code-only project. See [backfill without existing conventions](references/frozen-definitions.md#无现有组织规范时的默认回填).

Follow [the frozen-definition contract](references/frozen-definitions.md) for new or changed delivery tests. Each AT retains complete requirements, reverse rules and scenes in its own versioned `acceptance-catalog-v2`, with optional external references and actual user/contract origins. External sources may disappear without losing the execution baseline. A standalone adopted scene needs no invented parent requirement. Pending reverse observations remain separate from executable obligations.

All definition-dependent stages bind the exact immutable snapshot. The Agent supplies candidate full definitions and semantic impact assessment; deterministic compare/freeze detects changes and retains old versions. Revise scenes through the existing scenario workflow's edit mode: supply the old/new requirements and current adopted scenes, apply a version-bound delta, retain unchanged and human-edited content, and freeze the merged complete set. The host schedules execution from user intent: completing change acceptance includes every scene for affected requirements, including new/unexecuted scenes; otherwise changed scenes already executed are revalidated while new/unexecuted scenes remain unexecuted. An explicit design-only request launches no cases. Existing generated requests remain historical, never edited to match a new snapshot. Preserve previous judgments separately from whether they apply to the current definitions. Read the contract for the edit handoff, intent-bound v2 plans and legacy compatibility.

Adding an independent requirement does not invalidate unrelated scenes when only overall goals, scope, groups or workflow instructions expand. Business obligations belong in frozen requirements/rules or shared constraints; changes propagate through scene dependencies, while actual common constraints still affect all scenes. Preserve old receipt hashes through verified definition-history compatibility.

## Working sequence

First identify the user's project workspace from the task context. Store `.acceptance`, `.acceptance-local` and the sole `current.json` there; `acceptance.project_root` is that workspace, while `source_checkout` records the actual source location separately. Never move the store to a source checkout because it is a Git root. Startup, resume, init, execution guards and the project viewer reject a nested store beneath an existing project store and reject an isolated Git worktree as the store root, before creating files or running commands. Use the root named in the error; do not create another ID/pointer or rewrite frozen source paths to bypass it.

Before startup or resume, read `python3 <skill>/scripts/acceptance_store.py current <project-directory>`. `.acceptance-local/current.json` is the authoritative local pointer: one project, one person, one ongoing acceptance. No conversation binding is used. If absent, initialize a genuinely new acceptance or explicitly `start` the intended existing ID; never infer it from the newest config, history or browser selection. Every public workflow guard must match `config.acceptance.id` to this pointer before any project command or stage continuation. `init`/`start` refuse to replace another active ID. Retain the pointer across interruption, parked work and partial batches; after the whole acceptance has ended and its conclusion/unfinished limits are saved, call `finish <project-directory> <ID>` to clear only the matching pointer. A finished scene, closed conversation or terminal subworkflow does not end the entire acceptance. Viewing/switching IDs is read-only and never starts, switches or finishes execution. See [the current-acceptance lifecycle](references/project-acceptance-store.md#当前验收指针与启动恢复结束).

1. Apply the mandatory [project acceptance store contract](references/project-acceptance-store.md) before starting or resuming: one stable acceptance test ID (`AT-...`) under the user project, committed `.acceptance/<ID>` records, ignored `.acceptance-local/<ID>` execution assets, and shared `.acceptance/knowledge/INDEX.md`. An ID may cover multiple PRs/commits/requirements and survives scope and code changes; append scope versions and new dependent attempts instead of changing identity or overwriting old evidence. Read the root knowledge index and applicable child indexes/assets, record actual read hashes, and recheck at stage boundaries. New/updated knowledge must be reachable through layered indexes; stale reads, broken links and unindexed assets block continuation. Formal cases/fixtures/helpers belong to the existing project test framework and regression entry, not acceptance output directories; an isolated passed case is still a candidate until integrated. Preserve confirmed requirements and user decisions verbatim; do not copy secrets into either store. Historical paths are not silently migrated or assigned fabricated identities.
2. When original requirements exist, run [whole-list analysis](references/playbook-inputs-v3.md#whole-list-analysis) in create or edit mode. Its output is the overall business goal, confirmed scope and context-only requirement groups. Every input requirement remains included. The groups explain which requirements to consider together; they do not own scenes, set importance or become another acceptance data layer. User exclusions and unresolved business decisions stay explicit. This model-only flow has no Reviewer and must stop after its structural gate. For a code-only PR with no original requirement, skip this Playbook and supply an empty requirement list/groups plus a scope and goal anchored to user direction or existing independent contracts; do not invent a business goal from the implementation.
3. For each selected black-box requirement or supported white-box target, run [v4 one-target scenario generation](references/portable-workflow-v4.md#单目标场景) after step 4 when white-box is needed. Supply the *entire* requirements list, frozen goal/scope and relevant groups every time. Generated scenes have one main requirement or supported reverse rule; related requirements remain context. Existing or user-supplied scenes can be adopted directly; a standalone scene uses its own frozen agreement with no fabricated parent. Create scenes for missing coverage; after a requirement change, use edit mode to revise the current adopted set through a delta, preserving stable IDs and unaffected human edits. The scene is a concise test point: conditions, operation and expected outcome in one or two sentences. One Agent generates and internally checks coverage, importance, overlap and scope; its separate target self-check maps original obligations to scene IDs, concrete oracles and failure impacts, and a deterministic gate validates the bindings. A recorded design gap cannot count as tested coverage; explicitly permissive clauses are distinguished from unmet obligations. Check cross-target contradictions and materially duplicate purposes while retaining distinct assertions. This is **internal self-check, not independent scenario review**. If a user explicitly requires an independent scenario Reviewer, use the v3 scenario flow before execution.

   For a target involving visible UI or interaction, every scene also includes a visual usability criterion alongside task completion. Check that key controls and content are visible, readable and unobstructed, with sensible layout and visual hierarchy against the project's established style. Record UI relevance and each exact visual criterion in the target self-check; the gate binds them to the scenes. Do not create duplicate scenes solely for screenshots or infer unconfirmed brand rules.
4. For white-box work on a commit or PR, freeze the [complete change inventory](references/playbook-inputs-v3.md#one-commits-white-box-reverse-analysis): merge base, head, every changed path including declared Git submodules, and the project's non-test source paths. The current reverse route uses **one autonomous Agent in one continuous task**: it reads the frozen diff and necessary source, identifies important direct observable behavior changes, checks its own evidence, wording, overlap and likely major omissions, then submits one final result. There is no separate reverse Reviewer or review-revision loop. This is best-effort impact discovery, not a proof of completeness. Describe conditions and uncertainty accurately; do not turn speculative inputs or downstream effects into observed facts. The deterministic gate checks inventory disposition, source/version hashes, original requirement IDs and independent contract provenance; a contract snapshot from another Git repository must match its declared immutable commit and is rechecked downstream. Reuse behavior already covered by original requirements or confirmed rules; add a new supported rule only with independent basis. Park unresolved behavior as `needs_confirmation`; it cannot produce executable scenarios or product verdicts. Source code and a specification changed in the same PR do not establish their own expected behavior. A blocked or interrupted read-only reverse task starts a new frozen attempt unless a saved, valid final draft can be structurally resumed. Changed scope or PR head invalidates its dependent frozen work, not the stable acceptance test ID.

5. Prepare the project in two independent Agent tasks before case execution. First, a [runtime-preparation Agent](references/project-runtime-preparation.md) establishes and verifies this acceptance's project environment and existing test entry. When coverage is required, a separate [coverage-preparation Agent](references/project-coverage-protocol.md) consumes that frozen runtime record, chooses project-owned tools, and proves the collection chain with small non-business probes; skip this Agent when coverage is explicitly off. The host checks each Agent's files and actual environment before launching the next. Reusable setup knowledge and scripts are indexed under `.acceptance/knowledge`; installations, machine paths, probes and raw validation stay under this ID's ignored `.acceptance-local` or its dedicated workspace. A later acceptance reads the indexed knowledge but creates and verifies its own environment and coverage binding. Freeze the source inventory, component versions, runtime record, coverage adapter and necessary `coverage_test_files` in a new project catalog; later scenes inherit the exact verified entry and cannot silently downgrade it. Project commands, languages and tools are project data, never hard-coded Skill logic. Use one workspace at `.acceptance-local/<ID>/workspace` for sequential preparation and all scenes; product fixes require separate user authorization and a new frozen revision/catalog. Use [v4 shared preparation](references/portable-workflow-v4.md#项目只准备一次); project semantics are an operational guide, never a business oracle.
6. For each self-checked scene selected by the user's execution scope and intent, deterministically bind its exact version and run [v4 single-scene implementation, execution and independent review](references/portable-workflow-v4.md#单场景用例真实执行与独立复审). One case Agent may inspect source, reuse or implement a test and locally debug it through its generated, acceptance-bound debug entry; the host freezes an actual command, logs and file hashes; a separate read-only Reviewer checks implementation and evidence before deciding pass, product BUG, repair or blocker. A passing command and local Agent self-assessment are not a passed scene. Only concrete test-code/evidence gaps enter bounded differential repair and new frozen attempts. Scenario or contract questions park for a new scope/scene version. Product changes happen outside the test run and require a new frozen version. Use the v3 route when actual manual operation is required.

   Select `case_strategy: implement|existing_only` in the case template. The default implementation Agent retains design, reuse/new code and local debugging. The alternative existing-only Agent searches and actually debugs existing tests with the same result protocol, forbids test/source additions or edits, and never enters automatic test repair. Both feed a separate, read-only case-evaluation Agent that writes a human-facing coverage/quality/redundancy description. This description never changes test selection, launches repair/search, blocks execution or sets a product judgment; evaluation failure is recorded and execution continues. See [case Agents and descriptive evaluation](references/case-agents.md). The original frozen execution and independent Reviewer remain authoritative.

   Case implementation and differential repair run without SDK per-directory write grants or approval prompts. The acceptance-bound debug entry and host evidence/version checks remain the source of truth for the final result; do not treat unrestricted local debugging as a reviewed pass.

   For UI scenes, project preparation supplies the actual window/viewport, style reference and screenshot output paths; the case Agent captures key states in the formal execution. Freeze those screenshots with the same execution receipt. Attach the frozen image pixels as multimodal input to the independent Reviewer; a text path, DOM description or image file's existence does not prove visual inspection. The decision gate checks that cited screenshots match the images actually attached to that review. Missing or unviewable images mean UI is unverified and the scene cannot pass; a clear visual defect may be a product finding even when automated business assertions exit successfully. Archive the cited frozen images and show the UI result and screenshot links in the viewer. Historical functional-only results keep their original meaning.
7. Collect line and, where supported, branch coverage for the actual selected cases using the [mandatory coverage-tool contract](references/coverage-tool-contract.md). Use dedicated tools appropriate to each language/runtime and their supported conversion, source-map, merge and summary modules; **never implement custom coverage recognition, denominators, hit inference or transpilation reconstruction**. Preserve tool-generated zero-hit units. Declare `unavailable` or `incomplete` with concrete gaps when the evidence/toolchain is insufficient; reserve `off` for an explicit skip. Show collector/converter/statistics tool names and versions beside the metrics. Switching project, changed-file or changed-line scope recomputes both metrics from compatible tool reports. Missing reports, comments, blank lines and deletions cannot be fabricated as uncovered executable units. Coverage does not prove behavior correctness; coverage-driven enhancement remains separately opt-in.

Before declaring v4 preparation complete, apply the [preparation completion checks](references/portable-workflow-v4.md#项目只准备一次). Before ending the whole acceptance, apply the [acceptance-end checks](references/project-acceptance-store.md#验收结束与本机清理). Use the existing records and validators; these checks add no workflow stage or state and do not require project-specific infrastructure or CI where inapplicable.

When execution is requested, run P0 through P3 by default. Design/revision alone does not authorize execution of new or previously unexecuted scenes. Only an explicit user priority/time limit narrows the requested acceptance scope; design still covers all admitted requirements. Read [the shared importance standard](references/scenario-priority-v3.md) for both Analyst and Reviewer. P0 covers applicable core business closures and major risks; a later fix, rollback or valid-configuration adjustment does not downgrade a broken core path. Do not force a ratio or a P0 per requirement. Apply the same standard after repair and resume.

## Scope, handoff and recovery

Scope means the requirements, supported reverse rules and directly adopted scenarios admitted for this delivery test, plus explicit user exclusions and business decisions. A test about a neighboring function is admitted only when it directly proves a target requirement, is a necessary dependency to reach it, or checks an affected regression with a stated causal link. Keep unrelated ideas as suggestions, not as active scenes or mandatory resource gates. All roles and resumes use the same frozen scope and its version/hash; independent review cannot broaden it silently.

Every subworkflow stops at its own terminal or parked state. Model roles submit only their stage artifact; the host/scheduler alone starts the next stage. Preserve request, base/head commit, self-checked reverse result, analysis, scenario, catalog, code, execution and independent assessment hashes. The [v4 host](references/portable-workflow-v4.md#恢复边界) resumes an interrupted modifying Agent only after verifying the same session, frozen inputs, Git revision and changed test files. A missing execution receipt is never interpreted as failure or success; only an explicitly safe fresh isolated local retry can rerun. An unchanged parked repair remains parked without another model call or test run. Check the previous process is gone before resume. Changed scope, rule, scene or product version requires a new dependent frozen attempt under the same acceptance test ID; it does not erase the project's execution facts or latest confirmed scene result. Retain old evidence during acceptance and its actual version. After completed acceptance, preserve compact confirmed records and reproducible code/commands; raw logs, screenshots and coverage may be cleared under the [retention contract](references/project-acceptance-store.md#验收结束与本机清理).

For PR-wide conclusions, derive the complete target list from frozen behavior impacts. Every selected target must have its scenario list and every admitted scene an independent execution judgment; unresolved behaviors prevent a PR-wide pass. The v4 `run_plan.py` schedules declared target/scene jobs; its result alone is not a PR-wide verdict. Run [the v4 PR completion gate](references/portable-workflow-v4.md#单场景用例真实执行与独立复审) against v3 `pr-targets.json`, the exact plan and all frozen scene results before claiming a PR-wide pass or BUG. A changed PR head or source inventory starts a new downstream version.

## Live results and acceptance claim

Start the read-only viewer against exactly one user project directory as soon as acceptance begins. Discover `.acceptance` and `.acceptance-local` beneath it and select an acceptance test ID in the view; historical and current acceptances share the same entry:

```sh
python3 <skill>/scripts/v3/serve.py <project-directory> [--acceptance-id AT-<ID>]
```

It binds to 127.0.0.1 and refreshes every five seconds. Publish the project complete scenario catalog for the selected ID, including any target self-check design gaps as owner ID, exact quote and reason, and retain its execution/review records. Switching IDs replaces overview, traceability, progress, evidence and both coverage metrics together; it must not mix other IDs or scan nested worktrees. Missing complete catalogs suppress project ratios. Explicit historical imports retain their real provenance; an unrelated acceptance does not supply implicit pass results. Existing unregistered assets remain readable only via the explicit `--legacy-assets` viewer mode, without migration or execution. Frozen inputs appear first, then analysis or supported reverse rules, scenario generation, case preparation, actual execution, repair attempts and independent judgment. A v4 scene list is labeled internally self-checked; only scene execution receives independent review. The “正在处理” area appears only while work is running or waiting for repair/input; terminal work leaves this area and remains in the trace table. The table groups scenes under each original requirement or supported reverse rule; unexecuted items remain visible. Each scene retains its case/operation, actual execution, independent conclusion, actual evidence version and measured or unavailable code coverage. Long cells begin as three-line previews and expand on click. The JSON/evidence is authoritative; the viewer never runs tests or changes judgments.

### Project statistics contract

Use these definitions in every overview, JSON summary and scene row; see [the statistics contract](references/project-state-statistics.md) when implementing or checking a view.

- **Denominator:** for v2 every scene metric uses the selected AT’s complete current frozen scene collection, including unexecuted scenes; project SPEC items outside this test do not enter its denominator. Retired definitions remain historical. Legacy v1 views retain their recorded project catalog scope. Deduplicate by acceptance/project identity and stable scene ID. Never substitute an execution subset, priority or completed subset for that full frozen collection. The requirements denominator includes original requirements and admitted rules; unconfirmed candidate rules stay separate.
- **Executed:** a scene counts once as soon as one of its cases has actually been executed. Any prior execution counts, regardless of version, success, product-path completion, risk, evidence sufficiency or later repair. Case generation alone and an execution intent without an actual run do not count. An executed evidence-audit case counts as execution without proving the business path passed.
- **Result:** retain the scene's most recent confirmed conclusion. A new version, preparation, rerun or pending review does not erase it. “Needs revalidation” is a future action, not a result state. A first execution without a confirmed conclusion is pending confirmation; it cannot be invented as passed.
- **Accepted risk:** show it as its own result category, with an explicit user decision and evidence. It is neither passed nor an outstanding product BUG; keep the technical finding and decision provenance.
- **Reconciliation:** give every executed scene exactly one result category: passed, product BUG, accepted risk, repair/blocked (including insufficient evidence), or pending confirmation when no confirmed result exists. The category counts must sum exactly to the executed-scene count, with no overlaps or omissions. Unexecuted scenes do not enter these result counts. Display each nonzero category, and check the equality in the data and the rendered view.

Project result retention does not certify a new revision: preserve the real version/receipt/review sources, keep coverage scoped to its actual collection, and use the existing same-version completion gate for a release or PR-wide acceptance claim. Do not rewrite frozen evidence or rerun cases merely to make counters reconcile.

Do not call partial verification full acceptance. A requirement is accepted only when its scene list sufficiently covers the requirement, every admitted scene has a credible passed execution and independent judgment on the current frozen version, and no related blockers or exclusions are hidden. Under v4 the scene list has internal self-check rather than independent approval; disclose that assurance level when claiming sufficiency. Report product BUGs, test repairs, missing evidence, untested scope and coverage limits separately. A white-box/source rule cannot be passed merely because the implementation contains it.
