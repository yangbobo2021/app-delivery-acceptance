# 用例 Agent 与描述性评估

适用于 v4 自动化场景。共享运行与覆盖率环境仍按项目准备并复用；本地调试、正式冻结执行和执行后独立复审继续分开。

## 两种可替换的用例 Agent

在 `bind_case.py` 的模板（或 `run_plan.py` 的 `case_template`）声明：

```json
{
  "case_strategy": "existing_only",
  "case_evaluation": true
}
```

- `implement`（默认）：在同一会话先按[共同查找标准](case-search-guidance.md)检查已有用例，保存修改前的关联与引用，再决定复用、补充已有测试或为必要缺口新增测试，最后进行本地调试。不默认增加独立查找会话，已有支持充分时允许零修改。
- `existing_only`：已有用例查找 Agent。阅读实际输入、操作、断言、Fixture/Mock 和辅助代码，选择适用现有测试，用既有命令/过滤参数进行真实本地调试。不得新建、修改、删除用例、断言、Fixture、辅助、产品、SPEC、配置或锁文件；不制作新断言或业务请求冒充已有测试。调试请求和运行产物写在既有隔离目录。

两者输出同一协议：`status`、`test_files`、`test_command`、`test_env`、`observations`、`evidence_paths`、`limitations`、`reason`。本地 `passed_local` 不是正式场景通过。仅实际调试后才能记录执行观察；特殊宿主就绪情况仍按原 `host_ready` 语义披露未执行部分。

默认实现还须遵循[生成前复用契约](case-reuse-contract.md)，在修改或调试前通过宿主 checkpoint 固定真实已有用例，最终输出 `case_reuse`，逐项解释 `reuse`、`extend`、`new` 及找到但未采用项的原因。宿主校验当前场景、原文引用、来源身份和最终决策，分别保存 `case-reuse-discovery.json` 与绑定原回答的 `case-reuse.json`；无效结果不能当作用例就绪。原文快照只留在本机准备目录，不公开打包。最终独立评估阅读实际采用的完整用例组；早期复用说明不代替修复后代码与正式执行审查。维护此路径时使用[复用前向验证](case-reuse-validation.md)，核对实际改动和错误识别能力。

查找模式找不到测试或无法执行时，保留具体范围和原因；不自动切换到实现 Agent。`existing-files.json` 记录启动时的 Git 版本和可跟踪文件字节，宿主在调试与后续阶段核对，包括组件仓库和既有未提交测试。新增、修改或删除会触发原有文件保护；声称本地执行还必须存在实际调试收据。忽略的运行缓存不是业务测试来源；返回的测试文件须在启动记录中存在。

新查找任务同时遵循[已有用例查找契约](case-discovery-contract.md)：按项目实际入口、行为、参数和断言发现关联，返回 `case_discovery` 的检索范围、当前场景目标、逐用例贡献、重要排除候选及源码引用。宿主核对来源、连续引文、版本和双向关联后另存 `case-discovery.json`，原始 `answer.json` 保持不变；结构或引用无效不能当作有效查找结果。语言、框架和命令来自项目资料，宿主不按扩展名或命名规则推断测试语义。

需要纯静态关联时，直接调用 `run_existing_case_v1.mjs`，在其冻结场景输入中显式声明 `existing_case_mode: discover_only`。仍需合法验收绑定、当前指针和工作区租约；选择规则、说明和引用与普通查找模式相同，但只读、不建调试入口、不运行测试，结果为 `not_executed`。该结果只能作静态关联，不能传入正式场景执行流程冒充用例就绪；正式流程继续使用实际调试的默认模式。历史输出不被重新解释或补造新字段。维护查找 Agent 时，按[质量回归方法](case-discovery-validation.md)运行跨语言前向样例并独立核对语义；评测预期不进入 Agent 的场景输入或工作区。

查找模式禁止本地 blocker 修补及执行后自动测试修补。正式 Reviewer 仍按原规则返回实际结论，`repair_required` 保留为待处理，不暗中修改测试。默认实现模式的修补逻辑保持不变。

## 只给人看的用例评估

用例 Agent 产物之后、正式执行之前，独立只读 Agent 阅读实际关联用例，对以下内容作描述：

- 条件、操作、预期和多个用例的共同覆盖，列出实际依据与缺口；
- 质量风险，包括无效断言、过度约束、Mock 边界；
- 可能重复的范围及原因；
- 各用例的贡献和限制。

新输出采用 [`case-evaluation-v2` 结构化契约](case-evaluation-contract.md)：结论、场景原文义务及支持情况、必要缺口/设计问题/待确认/可选增强、逐用例贡献与取舍建议、逐目标生效/归属/结果核验，以及可核对的源码引用。评估前读取该契约。宿主核验路径、行号、连续原文、文件哈希和内部标识；引用可追溯不等于语义判断正确。历史输出保留原样展示，不补造引用。

已有本地观察只是背景，不能当作正式执行或独立验收结论。Agent 不运行测试，不改代码，不重新生成/查找一组用例，不移除关联，不筛选命令，不要求先修补再执行。`coverage: sufficient|partial|gap|uncertain` 是描述性标签，与源码行覆盖率、正式通过/BUG状态分开。

产物位于场景运行目录：

- `case-evaluation.json`：输入/用例/项目 catalog 哈希、可用性及完整描述。
- `case-evaluation.md`：人可直接阅读的报告，明确标注不参与执行控制。
- `case-evaluation-<用例结果哈希>/`：原始输入、Agent 回答与模型运行记录。
- 最终 `summary.json.case_evaluation`：描述或失败原因；正式结论仍读取原 `review_status`。

评估阶段保留600秒的有界等待，以容纳必要源码与复合响应的核验。相同绑定恢复时复用已有描述。失败、超时、格式异常均记录为不可用，不阻止执行、不自动重试评估，也不计入执行状态机门禁或修补计数。原正式 Reviewer 不消费该描述作为判定依据。

结果视图在每个场景的用例列表下展示独立描述，明确标注评估来源；不新增正式结果分类。默认仅展示评估标题及支持程度，展开后先显示简洁结论、必要缺口和取舍建议；场景逐项依据、设计问题、可选增强、逐用例贡献与源码引用继续折叠查看。用例说明和评估按[统一展示契约](case-display-contract.md)分开呈现。正式归档会带上存在的描述报告和其回答，不将模型会话、调试产物或凭据一并公开。

`--stop-after case` 仍在原用例阶段后停下；`--stop-after case-evaluation` 是调用者主动选择在描述后暂停，不代表评估 Agent 否决后续执行。该暂停位置记录在原流程状态文件的宿主检查点中，视图不再将其显示为正在运行；恢复时先清除检查点，再继续真实阶段，不改写已发生的本地调试和正式结论。`case_evaluation: false` 可显式跳过描述，已冻结的配置不得原地修改。

## 静态关联展示

只读项目结果视图支持 `.acceptance/<ID>/tests.json` 的 `static-existing-tests-v1`：

- `acceptance_id` 必须为当前查看的 ID；`tests` 记录唯一 `id`、`title`、相对冻结工作区的 `file`、`file_sha256`，以及可选的行号、`revision`、输入操作、断言、贡献、Mock 边界和限制。
- `scene_mappings` 记录当前冻结场景 `scene_id`、关联 `test_ids`、`mapping_basis` 与 `missing_or_uncertain`。空关联明确表示静态检索未找到用例；不表示整个项目不存在测试。
- 视图将这些信息展示在现有“追踪关系”表格的“用例／操作”列，即使用例尚未执行。展开可查看依据、源码版本和限制；源码工作区缺失或文件哈希变化时保留原关联并明确提示。
- 该文件只提供静态关系，不构成 Case Agent 准备完成、运行时收集、执行收据或正式 Reviewer 结论。执行情况和独立结论继续读取原协议；不因关联数量改变已执行、通过、BUG 或代码覆盖率统计。查看不会启动验收或测试。

生成、查找和差量修复 Agent 的 `case_descriptions` 使用[统一用例说明契约](case-display-contract.md)，来自实际测试代码。缺失字段不由视图推断。

三个角色共用其中的标题质量标准：必要条件和真实验证行为要直接可读，详细步骤、样本数据和实现方法放在展开信息中；提交前单独阅读标题列表自查自然度、区分度和准确性。维护时用实际生成与查找产物阅读复核，不能以包含中文、字数短或禁用某个词就断言标题质量合格。
