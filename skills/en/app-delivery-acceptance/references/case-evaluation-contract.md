# 场景关联用例评估契约

评估服务于用户的三个决定：当前关联用例能否验证这个场景，缺什么，以及哪些用例值得保留。只读实际测试及必要依赖。先把**当前场景**拆成少量可核对的条件、操作和预期，逐项评价用例组的共同贡献；上层需求、相邻场景、实现机制仅作理解背景，不自动增加本场景的义务。显式 UI 标准属于场景义务。

必要缺口必须同时指出：场景原文、实际测试依据、以及现有断言可能放过的具体错误行为。缺少执行记录只限制运行结论，不自动成为设计缺口。测试层级、Mock、代表值本身不构成不足；判断它们是否遮住当前场景要求的行为。只有场景要求完整链路时才要求贯通；从准备好的合法记录开始的 UI 场景不必重新验证记录生产流程。未要求的内部持久化、更多组合、诊断文案或其他入口可省略，确有价值才列为可选增强，不能降低支持程度。

先核对输入和前置条件，再看操作、断言及辅助函数；名称、前一 Agent 的说明和源码实现不能代替测试的断言。参数或提前返回的含义需结合被调函数才能确定时，核对必要实现再解释测试；不能仅因缺某个参数就断言测试走了错误分支，无法核对时标待确认。区分缺少业务断言、空断言、脆弱附加约束与无法核对。不要因任意异常断言就要求未约定的异常类型，也不要把合理的有限样本说成穷尽证明。

对否定断言或聚合结果，检查本次操作是否被接受/生效、目标对象是否存在、结果是否确实归属它。若目标记录被丢弃、聚合响应只含其他记录仍能通过，就是缺口；不机械要求每步状态码，等价的生效与归属证据也成立。区分最终值与动作事实：内容保持相同不能单独证明从未写入，一次上游调用不能证明下游只写一次。建议优先补足场景可观察预期，不把特定进程数、内部调用方式等实现选择变成必需约束。前置条件未被场景要求时，须说明其变化如何遮住当前义务，不能仅因与另一用例不同而判为设计缺陷。冲突或优先级场景须明确由哪个字段及取值决定结果，摘要与细节不能反转该依据。

逐用例比较条件、操作、断言、测试层级与本场景的增量贡献。标明关键、互补、重复、场景外或待确认；判重复时引用对照用例，不按名称、相同返回值或同一行覆盖认定重复。其他场景的独有断言不能成为在本场景保留的理由。取舍建议只供人决定，不删除关联、改变执行列表或发起修补。场景外用例仍可能是有价值的回归测试。

## 输出

只输出下列 JSON，使用与场景一致的语言，技术标识保留原文。先写一句结论和决定性原因；每个字段只讲一件事，避免复述、长免责声明或逐项重复静态评估限制。空组只说明当前关联为空，不能声称整个仓库无用例。无需为没有发现的问题凑条目。

```json
{
  "schema": "case-evaluation-v2",
  "summary": "180字以内：支持程度、决定性原因",
  "coverage": "sufficient|partial|gap|uncertain",
  "obligations": [
    {"id":"O1","quote":"当前场景中的原文片段","status":"supported|partial|unsupported|uncertain","assessment":"实际支持及缺口，160字以内","evidence_ids":["E1"]}
  ],
  "findings": [
    {"id":"F1","kind":"gap|quality|uncertainty|enhancement","obligation_ids":["O1"],"statement":"问题，180字以内","impact":"可能放过的具体错误行为，或附加约束的实际代价，200字以内","recommendation":"最小有效改进，180字以内","evidence_ids":["E1"]}
  ],
  "case_assessments": [
    {"case_id":"C1","role":"essential|complementary|duplicate|out_of_scope|uncertain","contribution":"对本场景的增量贡献与取舍理由，180字以内","compared_with":[],"evidence_ids":["E1"],"checks":[{"target":"本场景内的一个操作及其结果目标","assessment":"提交/操作是否生效、如何定位本次目标、实际结果断言及可能空通过的原因，180字以内","counterexample":"仅移除或破坏当前目标，保留其他合法数据，现有断言能否通过及依据，180字以内","evidence_ids":["E1"]}]}
  ],
  "selection_advice":"180字以内：建议保留的用例组、重复项的取舍及仍需补足的内容；不要声称有缺口的组已经足够",
  "limitations":["最多3项，仅列影响理解的限制"],
  "evidence": [
    {"id":"E1","file":"相对源码工作区的真实文件路径","line_start":1,"line_end":3,"quote":"该行范围内的连续原文，保留空白，不加行号、省略号或改写"}
  ]
}
```

宿主提供稳定 `C1…` 用例标识；每项恰评估一次。`compared_with` 引用其他用例标识；重复项须给出对照及双方证据。`evidence_ids` 只引用本次证据；每项用例评价须有其测试正文依据，支持结论亦须有依据。已读取但没有关键断言时，可引用相关测试正文说明缺少什么；文件不可读时明确待确认，不伪造引用。引用尽量小，一段不超过30行/1800字，可拆分多段。必要缺口关联当前场景义务；可选增强与必要缺口分开，至多列2项可选增强，总问题至多6项，优先决定性问题。关联为空时可用 gap、全部义务 unsupported 和空 findings/证据，避免重复陈述同一个“无关联”事实。有限样本的充分性是设计判断，不是业务验收通过或覆盖率统计。

宿主校验结构、引用标识、场景摘录、文件边界、行号、原文和文件哈希，并将实际哈希写入证据。该核验只确认引用可追溯，不证明语义判断正确。仅当原文在整个文件中唯一、起始行准确且结束行恰好少1行时，宿主可由原文确定正确结束行并记录原行号；不改原文、不挪到另一测试、不接受歧义匹配。其他校验失败保存原始输出并标记说明不可用，原执行继续，不自动重试。旧报告继续按原协议展示，不补造结构或引用。

每项用例的 `checks` 是逐目标核验记录，不是重复摘要。一个用例提交多个独立对象、报告或入口时，逐个列出相关操作及其输出目标，分别检查“是否生效→目标是否存在且归属本次操作→结果断言是否有效”。否定断言需逐项做反例检查：若本次操作完全无效、目标为空，或标记仅来自另一条记录，整条测试是否仍能通过？不能只对组中最明显的一项这样检查，不能以另一入口的存在性断言代替当前入口。将发现的决定性漏洞合并回必要缺口，并限定摘要中的支持范围；前置对象由可靠 Fixture 保证或已有等价肯定断言时说明依据即可，无需额外强求状态码。

核验响应时先阅读必要的 mock/辅助函数/响应构造，明确整个观察对象由哪些独立记录或子对象组成，并引用该结构。`counterexample` 必须只移除或破坏**当前目标子对象**，保留同一响应中的其他合法对象、既有错误与标记，再按实际断言判断；不要把整个响应清空当成这个反例。整个响应非空、含某个通用标记，只能证明有其他内容，不能证明目标子对象存在。若不能核对观察对象的结构，不得肯定归属成立，应标待确认并说明影响。
