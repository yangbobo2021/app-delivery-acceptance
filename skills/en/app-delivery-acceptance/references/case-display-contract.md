# 用例说明与结果视图

“用例／操作”列回答：怎么测、验证什么、可信边界，以及用例组还存在哪些缺口。实现、复用查找与差量修复 Agent 使用相同的展示字段；这些说明不构成执行事实或正式验收结论。

在原有结果 JSON 中增加 `case_descriptions` 数组，每个实际业务测试项一条：

```json
{
  "case_descriptions": [{
    "id": "本次结果内唯一引用；宿主会替换为永久用例 ID",
    "name": "与用户及页面语言一致，用一句自然的话说明必要条件和实际验证的行为或结果",
    "method": "关键前置条件、输入和操作；必要时说明步骤",
    "assertions": "最终代码实际检查的结果与检查方式",
    "boundary": "测试层级、关键 Mock、隔离条件、未验证部分和其他限制",
    "source": {
      "origin": "existing 或 generated",
      "file": "项目内测试文件相对路径",
      "title": "代码中的真实测试项标题",
      "line_start": 1,
      "line_end": 10,
      "id_comment": "// {id}"
    }
  }]
}
```

根据最终实际测试代码整理；不得照抄场景预期当成已有断言，不把计划当成已经实现的检查，不把测试退出成功当成每个业务断言已被独立确认。实现 Agent 复用的已有测试仍标记 existing；只有实际新增测试才标记 generated。`test_files` 仍用于原执行协议；Fixture、配置和辅助文件不独立冒充业务测试项。无法确认的信息留空并在限制中披露。未找到测试时数组为空。

## 标题质量：不展开也能看懂测什么

生成、查找和差量修复 Agent 都按同一标准填写 `name`。标题面向需要判断测试价值的人，使用用户及视图的语言，以一句自然短句说明**必要条件和实际验证的行为或结果**。不要求所有标题套同一个句式，不用截断或机械替换词语来缩短标题。

- 写清业务对象和结果，保留区分相邻用例所需的条件。避免“正常测试”“边界验证”“处理成功”等没有具体行为的标题。标题可以省略场景中不影响区分的步骤，但不能只剩“成功”“不变”等失去对象的结论。
- 标题概括主要行为，不承担列出全部输入组合和断言的职责。一个用例核对多项结果时，突出最能说明其价值的行为；其他断言可以放在详情中。概括已测行为不等于声称穷尽所有组合，但不能换成代码没有检查的目标、条件或结果。
- 不把操作过程逐句搬进标题。具体样本值、调用顺序、函数名、变量名、断言方法、Mock、计数器和字节比较通常放到 `method`、`assertions`、`boundary`。数值本身就是业务门槛或错误条件时可以保留；协议状态码等对读者有意义的术语也可以保留。
- 条件和对象要具体，避免“参数、文件值、覆盖”等泛称让读者猜含义。必要的领域术语可以使用，例如区分配置来源时的命令行参数、环境变量和配置文件；不要为了避开术语换成含义不明的“外部设置”。
- 精简不能丢失关键对象：“未提供某个业务参数”不等于“没有任何命令行参数”。例如测试未通过命令行指定根目录，但仍传入配置文件路径时，要写清未指定的是根目录，而非声称未设置命令行参数。环境变量的表述也应限定到所测业务对象，不暗示整个进程没有其他环境变量。
- 只写实际测试能够支持的结果。仅断言请求或替身调用时，用“请求清除”“发出通知”等准确表述，不能写成浏览器已清除或外部消息已送达。弱断言不能借标题升级为完整业务保障；内部保存计数也不能写成已经验证真实持久化。
- 使用自然陈述，通常不需要“检查……”“验证是否……”的操作口吻。若它们有助于准确表达观察边界，可以保留，不能为追求顺口而夸大实际支持。

以下是表达方式示例，不是项目或语言规则：

| 难读或不准确 | 更好的标题 |
| --- | --- |
| 参数、环境变量和文件值同时存在时，输出命令行指定的目录 | 根目录优先使用命令行参数 |
| 没有参数和环境变量覆盖时，输出配置文件中的目录 | 未通过参数或环境变量指定根目录时，使用配置文件 |
| 参数和环境变量同时覆盖时，检查配置文件字节保持不变 | 指定根目录后，配置文件保持原样 |
| 余额30时取31被拒绝，检查余额仍为30 | 余额不足时拒绝取款，且余额不变 |
| 断言响应替身收到清理会话Cookie的方法调用 | 注销时请求清除会话 Cookie |
| 只检查清除方法的调用，却命名为“注销后浏览器Cookie已清除” | 注销时请求清除会话 Cookie |

**提交前单独读一遍所有 `name`，不依赖展开内容自查并修订**：读者能否直接知道每项测什么；相邻标题能否分清差别；是否混入不必要的代码、数据或步骤；结果是否比实际断言更强。以实际输入、操作和断言复核准确性，不凭标题听起来像业务目标就接受。不另加标题评估字段或模型调用，也不为美化标题修改复用测试的代码标题。

代码中的原始标题保留在 `source.title` 供溯源。视图默认仅展示 `name`；点击名称打开用例详情弹窗，分别阅读测试方法、验证内容与验证边界、来源与执行入口。整组用例设计评估保留单独的详情入口。历史产物缺少字段时显示“未说明”，不能从执行观察或场景预期补造说明。

独立评估 Agent 的原生 `case-evaluation.json` 在场景用例列表下显示支持程度和必要缺口入口；详情呈现摘要、完整支持范围、缺口、质量、重复范围及逐用例贡献。它与用例 Agent 自述明确区分；缺失、关闭、失败或版本失配时如实显示状态。源码行覆盖率、实际执行、正式 Reviewer 结论仍读各自原始协议，不受展示字段影响。

历史用例可在 `.acceptance/<ID>/case-display.json` 记录纯展示名称（`acceptance-case-display-v1`，含 acceptance_id、language 和 cases 数组）。每项包含 id、name、source_title、file_sha256；仅在原始用例 ID、标题和源文件哈希匹配时应用，不改写冻结输入或独立评估。

## 统一追踪与详情

正式查看器遵循 [追踪关系视图合同](traceability-view.md)：保留五列关系，以简洁标题、数量、设计评价、执行事实和确认结论支持扫读；完整说明在“概览／关联关系／依据与记录”弹窗中阅读。需求、场景、用例、用例组设计评价、实际执行和独立结论使用同一详情结构，关联跳转可返回，不叠加弹窗。

用例列默认保留前三项可读名称和全部入口，结构化必要缺口数与设计评价可直接查看；逐用例方法、实际断言和边界进入概览。表格不再显示“关联说明（查找阶段）”；组级关联依据放在场景详情，逐项原因仅在有实际记录时展示。执行和确认结论各读其实际记录，不从展示说明推断。

理解需求的 Agent 可在 `.acceptance/<ID>/requirement-display.json` 保存阅读说明，不额外调用模型或在浏览时临时总结。使用 `schema: acceptance-requirement-display-v1`、`acceptance_id` 和 `requirements` 数组；每项含 `id`、`title`、`summary`、可选的 `rules` 字符串数组，以及原始 `text` UTF-8 字节的 SHA-256 `text_sha256`。标题和摘要使用用户语言，交代业务目标、必要条件与结果；逐项核对重要例外和边界，不把抽样场景的范围改写成整个需求的范围。

这些字段只供阅读，冻结需求及其判定依据保持原样。哈希不符时停用旧摘要并提示原文已变化；历史记录没有阅读说明时使用已有标题和完整原文，不截取正文冒充摘要。执行统计、用例关联及独立评估不因展示资料改变。

## 永久用例 ID：关联后由宿主统一落地

仅为本场景实际采用的业务测试项标记 ID；不批量扫描或改写全部测试。查找、实现、修复 Agent 均须提供准确的 `source.file/title/line_start/line_end`，范围从**完整测试声明**开始（包含装饰器、属性），到该项测试结束；已有 `@case-id` 注释在范围外、紧邻声明上一行。脚本级测试保留 shebang、编码声明等文件头，定位到安全的业务入口前。参数化声明共享一个 ID；不同业务测试应有可独立定位的声明或数据条目，无法准确定位时报告限制，不凭标题猜测身份。

`source.id_comment` 给出该位置合法的单行注释模板，含一个 `{id}`，例如 `# {id}`、`// {id}`、`-- {id}`、`/* {id} */`、`<!-- {id} -->`。必须确认该行处于源码注释位置，不能在字符串、here-document、模板文本或其他数据内部。不是让 Agent 选择项目适配器；按实际语法提供模板。不支持的语法或不安全的位置如实阻塞，不能用无效注释破坏代码。Agent 不自行生成、修改或移动永久 ID，也不能制造 `case_identity` 宿主报告。修复已有测试保留它的 ID 注释，确实新建的测试不复制旧 ID。查找 Agent 仍只读。

宿主在校验原始查找/复用结果后、正式执行冻结前，生成 `TC-<UUIDv4>`，仅插入普通注释 `@case-id: TC-…`。已有标记优先复用；重复 ID、错位标记、源码引用不符会阻止交接。中文名称、文件移动、断言补充不要求重编 ID；完整标记须随声明移动。

宿主保存 `answer.agent.json` 原始结果、`case-identities.json` ID 与源码绑定及精确注释补丁，并更新 `answer.json` 的关联引用、行号、哈希。跨声明的原引用因插入注释需要扩展时，保留 `quote_before_identity`，新引用只按实际源码重取。旧调试凭证不改写；正式宿主执行绑定添加 ID 后的文件。`existing_only` 仅允许这份经过核对的宿主 ID 注释补丁，其余源码、文件集合、模式和断言保持原样。

项目共享 `.acceptance/case-identities.json` 保存 ID 和场景关联，随项目提交。它不是全项目用例清单：仅包含本 SKILL 实际采用的项。尚未合入原仓库的候选代码缺少标记时，只有文件、原始标题与测试正文完全一致才沿用已记录 ID；移动或改写且丢失注释时不能自动认定为旧用例。隔离工作区的候选身份不冒称已经集成到主干。

用例详情沿用统一弹窗，展示永久 ID、源码位置；历史记录保留原有局部 ID，不追溯改写。评估中 `C1` 等短引用通过 `original_id` 对应永久 ID。命令执行凭证只证明所绑定文件与命令的实际执行，不能据此声称每个关联 ID 都单独执行通过。
