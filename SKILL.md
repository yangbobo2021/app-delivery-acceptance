# App delivery acceptance

Use this Skill to turn confirmed requirements into test scenarios and, when an implementation is available, to execute cases and reach evidence-based delivery judgments. Preserve the original requirements verbatim and retain their stable IDs. Code-derived rules are separate sources; confirm their intended behavior before treating them as acceptance obligations. A source branch or nearby feature does not by itself expand the user's test scope.

The current route is **v4** for frozen Git projects with locally executable automated tests: v3 whole-list analysis and white-box reverse analysis feed v4 one-target scenario generation, shared project preparation and one-scene implementation/execution/review. The v4 stage runners are single-Agent tasks with deterministic handoffs; only case execution receives a separate independent Reviewer. Use the [v4 operating contract](references/portable-workflow-v4.md) for this route. Keep the [v3 portable route](references/portable-workflow-v3.md) for source-free black-box and actual manual operations; a v4 automated run must never fabricate either. Do not start older acceptance-organization Playbooks or create acceptance-unit ownership.

## Working sequence

1. Freeze the complete confirmed requirements, user decisions and chosen test-assets directory. Reuse a directory already supplied by the user; otherwise use the project's normal test-assets area unless a material placement constraint needs clarification. Keep executable tests in the project's conventional test tree and results/evidence in the selected assets. Do not copy secrets into either.
2. When original requirements exist, run [whole-list analysis](references/playbook-inputs-v3.md#whole-list-analysis) in create or edit mode. Its output is the overall business goal, confirmed scope and context-only requirement groups. Every input requirement remains included. The groups explain which requirements to consider together; they do not own scenes, set importance or become another acceptance data layer. User exclusions and unresolved business decisions stay explicit. This model-only flow has no Reviewer and must stop after its structural gate. For a code-only PR with no original requirement, skip this Playbook and supply an empty requirement list/groups plus a scope and goal anchored to user direction or existing independent contracts; do not invent a business goal from the implementation.
3. For each selected black-box requirement or supported white-box target, run [v4 one-target scenario generation](references/portable-workflow-v4.md#单目标场景) after step 4 when white-box is needed. Supply the *entire* requirements list, frozen goal/scope and relevant groups every time. Each scene has exactly one main requirement or supported reverse rule; related requirements are context and receive their own scene lists in separate runs. The scene is a concise test point: conditions, operation and expected outcome in one or two sentences. One Agent generates and internally checks coverage, importance, overlap and scope; a deterministic gate validates the final structure. This is **internal self-check, not independent scenario review**. If a user explicitly requires an independent scenario Reviewer, use the v3 scenario flow before execution.
4. For white-box work on a commit or PR, freeze the [complete change inventory](references/playbook-inputs-v3.md#one-commits-white-box-reverse-analysis): merge base, head, every changed path including declared Git submodules, and the project's non-test source paths. The current reverse route uses **one autonomous Agent in one continuous task**: it reads the frozen diff and necessary source, identifies important direct observable behavior changes, checks its own evidence, wording, overlap and likely major omissions, then submits one final result. There is no separate reverse Reviewer or review-revision loop. This is best-effort impact discovery, not a proof of completeness. Describe conditions and uncertainty accurately; do not turn speculative inputs or downstream effects into observed facts. The deterministic gate checks inventory disposition, source/version hashes, original requirement IDs and independent contract provenance; a contract snapshot from another Git repository must match its declared immutable commit and is rechecked downstream. Reuse behavior already covered by original requirements or confirmed rules; add a new supported rule only with independent basis. Park unresolved behavior as `needs_confirmation`; it cannot produce executable scenarios or product verdicts. Source code and a specification changed in the same PR do not establish their own expected behavior. A blocked or interrupted read-only reverse task starts a new frozen attempt unless a saved, valid final draft can be structurally resumed. Changed scope or PR head invalidates its dependent work.

5. Prepare a reusable project catalog once per frozen project version: relevant existing tests, fixture/setup capabilities, real executors, source inventory, component versions and available coverage collectors. For continuous coverage, verify the actual registered toolchain/runtime adapters first, freeze a tool-owned complete denominator, and store the provider configuration in the catalog and activate the repository policy so every later scene inherits the same execution entry. Old templates cannot silently disable collection; a new revision requires newly verified preparation. Project commands and paths are input data, never hard-coded Skill logic. Each automated scene uses an isolated worktree from that frozen version. Use [v4 shared preparation](references/portable-workflow-v4.md#项目只准备一次); project semantics may be prepared once as an operational guide, never as a business oracle.
6. For each self-checked scene, deterministically bind its exact version and run [v4 single-scene implementation, execution and independent review](references/portable-workflow-v4.md#单场景用例真实执行与独立复审). One case Agent may inspect source, reuse or implement a test and locally debug it within declared test roots; the host freezes an actual command, logs and file hashes; a separate read-only Reviewer checks implementation and evidence before deciding pass, product BUG, repair or blocker. A passing command and local Agent self-assessment are not a passed scene. Only concrete test-code/evidence gaps enter bounded differential repair and new frozen attempts. Scenario or contract questions park for a new scope/scene version. Product changes happen outside the test run and require a new frozen version. Use the v3 route when actual manual operation is required.
7. Collect line and, where supported, branch coverage for the actual selected cases using the [mandatory coverage-tool contract](references/coverage-tool-contract.md). Use dedicated tools appropriate to each language/runtime and their supported conversion, source-map, merge and summary modules; **never implement custom coverage recognition, denominators, hit inference or transpilation reconstruction**. Preserve tool-generated zero-hit units. Declare `unavailable` or `incomplete` with concrete gaps when the evidence/toolchain is insufficient; reserve `off` for an explicit skip. Show collector/converter/statistics tool names and versions beside the metrics. Switching project, changed-file or changed-line scope recomputes both metrics from compatible tool reports. Missing reports, comments, blank lines and deletions cannot be fabricated as uncovered executable units. Coverage does not prove behavior correctness; coverage-driven enhancement remains separately opt-in.

Run P0 through P3 by default. Only an explicit user priority/time limit narrows execution; design still covers all admitted requirements. Read [the shared importance standard](references/scenario-priority-v3.md) for both Analyst and Reviewer. P0 covers applicable core business closures and major risks; a later fix, rollback or valid-configuration adjustment does not downgrade a broken core path. Do not force a ratio or a P0 per requirement. Apply the same standard after repair and resume.

## Scope, handoff and recovery

Scope means the original requirements and code-derived rules admitted for this run, plus explicit user exclusions and business decisions. A test about a neighboring function is admitted only when it directly proves a target requirement, is a necessary dependency to reach it, or checks an affected regression with a stated causal link. Keep unrelated ideas as suggestions, not as active scenes or mandatory resource gates. All roles and resumes use the same frozen scope and its version/hash; independent review cannot broaden it silently.

Every subworkflow stops at its own terminal or parked state. Model roles submit only their stage artifact; the host/scheduler alone starts the next stage. Preserve request, base/head commit, self-checked reverse result, analysis, scenario, catalog, code, execution and independent assessment hashes. The [v4 host](references/portable-workflow-v4.md#恢复边界) resumes an interrupted modifying Agent only after verifying the same session, frozen inputs, Git revision and changed test files. A missing execution receipt is never interpreted as failure or success; only an explicitly safe fresh isolated local retry can rerun. An unchanged parked repair remains parked without another model call or test run. Check the previous process is gone before resume. Changed scope, rule, scene or product version requires a new dependent frozen attempt or run; it does not erase the project's execution facts or latest confirmed scene result. Retain old evidence and its actual version.

For PR-wide conclusions, derive the complete target list from frozen behavior impacts. Every selected target must have its scenario list and every admitted scene an independent execution judgment; unresolved behaviors prevent a PR-wide pass. The v4 `run_plan.py` schedules declared target/scene jobs; its result alone is not a PR-wide verdict. Run [the v4 PR completion gate](references/portable-workflow-v4.md#单场景用例真实执行与独立复审) against v3 `pr-targets.json`, the exact plan and all frozen scene results before claiming a PR-wide pass or BUG. A changed PR head or source inventory starts a new downstream version.

## Live results and acceptance claim

Start the read-only viewer as soon as the run begins. Pass the directory containing this run's workflow output folders, including their `request.frozen.json` files; a `trace.json` path alone can show only completed execution:

```sh
python3 <skill>/scripts/v3/serve.py <project-assets-directory> [other-project-history-directory ...]
```

It binds to 127.0.0.1 and refreshes every five seconds. Supply the complete project scenario catalog and its execution/result directories, including prior attempts; a selected batch alone cannot supply a project-wide denominator. Frozen inputs appear first, then analysis or supported reverse rules, scenario generation, case preparation, actual execution, repair attempts and independent judgment. A v4 scene list is labeled internally self-checked; only scene execution receives independent review. The “正在处理” area appears only while work is running or waiting for repair/input; terminal work leaves this area and remains in the trace table. The table groups scenes under each original requirement or supported reverse rule; unexecuted items remain visible. Each scene retains its case/operation, actual execution, independent conclusion, actual evidence version and measured or unavailable code coverage. Long cells begin as three-line previews and expand on click. The JSON/evidence is authoritative; the viewer never runs tests or changes judgments.

### Project statistics contract

Use these definitions in every overview, JSON summary and scene row; see [the statistics contract](references/project-state-statistics.md) when implementing or checking a view.

- **Denominator:** every scene metric uses all scenes in the project, deduplicated by project ID and scene ID, including unexecuted scenes. Never substitute a selected/basic batch, current version, priority or completed subset. The requirements denominator includes original requirements and admitted rules; unconfirmed candidate rules stay separate.
- **Executed:** a scene counts once as soon as one of its cases has actually been executed. Any prior execution counts, regardless of version, success, product-path completion, risk, evidence sufficiency or later repair. Case generation alone and an execution intent without an actual run do not count. An executed evidence-audit case counts as execution without proving the business path passed.
- **Result:** retain the scene's most recent confirmed conclusion. A new version, preparation, rerun or pending review does not erase it. “Needs revalidation” is a future action, not a result state. A first execution without a confirmed conclusion is pending confirmation; it cannot be invented as passed.
- **Accepted risk:** show it as its own result category, with an explicit user decision and evidence. It is neither passed nor an outstanding product BUG; keep the technical finding and decision provenance.
- **Reconciliation:** give every executed scene exactly one result category: passed, product BUG, accepted risk, repair/blocked (including insufficient evidence), or pending confirmation when no confirmed result exists. The category counts must sum exactly to the executed-scene count, with no overlaps or omissions. Unexecuted scenes do not enter these result counts. Display each nonzero category, and check the equality in the data and the rendered view.

Project result retention does not certify a new revision: preserve the real version/receipt/review sources, keep coverage scoped to its actual collection, and use the existing same-version completion gate for a release or PR-wide acceptance claim. Do not rewrite frozen evidence or rerun cases merely to make counters reconcile.

Do not call partial verification full acceptance. A requirement is accepted only when its scene list sufficiently covers the requirement, every admitted scene has a credible passed execution and independent judgment on the current frozen version, and no related blockers or exclusions are hidden. Under v4 the scene list has internal self-check rather than independent approval; disclose that assurance level when claiming sufficiency. Report product BUGs, test repairs, missing evidence, untested scope and coverage limits separately. A white-box/source rule cannot be passed merely because the implementation contains it.
